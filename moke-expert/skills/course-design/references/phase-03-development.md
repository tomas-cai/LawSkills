# 开发阶段参考（Phase 03 - Development）

## 节奏选择

进入本阶段时，先判断用户状态来决定执行节奏：

| 用户特征 | 使用模式 | 做法 |
|:---|:---|:---|
| 消息中包含多个信息点，能一次性回答多个问题 | **批量模式**（默认） | 将下面的核心问题一次性抛出，用户集中回答后统一处理 |
| 消息简短、表示不确定、需要引导 | **逐题模式** | 按下面的探索问题逐个深入追问 |

### 批量模式：核心问题

- 每个模块的核心内容方向
- 实操案例的场景选择（几个案例？难度递进？）
- 测评形式与评分标准的细节确认

### 逐题模式：深入探索

- 讲师话术的关键节点与逐字稿
- 视觉设计的风格要求
- 敏捷验证节点（P2/P3）的排期
- 案例的参考答案不同水平分级

## 第一节：教学内容开发规范

### 四侧材料体系

每门课程需要开发四类材料：

| 材料侧 | 内容 | 受众 | 关键标准 |
|:---|:---|:---|:---|
| **学员侧** | 讲义、课件、学习手册 | 学习者 | 自学友好、结构清晰、重点标注 |
| **讲师侧** | 讲师引导手册、逐字稿 | 讲师 | 含时间把控、关键话术、应急预案 |
| **实操侧** | 案例说明、练习指南、参考答案 | 学习者+讲师 | 场景真实、步骤明确、难度递进 |
| **测评侧** | 测评题目、评分标准、答案解析 | 学习者+讲师 | 目标-测评对齐、评分标准可操作 |

### 内容写作原则

1. **每个模块一个核心观点**：不要在一个模块里塞多个独立概念
2. **先建立"为什么"再讲"是什么"**：先说明这个知识点解决了什么痛点
3. **使用案例贯穿**：每个抽象概念配一个具体案例
4. **图表优先于文字**：能用图/表/模型表达的就不要用段落
5. **总结+预告**：每个模块结束时做要点回顾并预告下个模块

### 跨模块技能的设计原则

有些技能不属于任何一个单独的模块，而是需要贯穿多个模块（如 Git 版本管理、
文档治理、AI 工具操作习惯）。处理原则：

| 错误做法 | 正确做法 |
|:---|:---|
| 单独开一堂"Git 课" | **分散融入**：首次用到时教基础操作，后续每次用到时加深 |
| 只在某一天讲一次 | **螺旋上升**：M1 知道概念 → M3 首次实践 → M5 系统讲解 → M7 实战应用 |
| 不教就要求用 | **搭脚手架**：模板化操作步骤，学员先复制再理解 |

**以 Git 为例的正确融入方式**：
- M3（首次接触代码）：教 git init / add / commit 三个命令就够了
- M4-3（产出规范文件后）：首次 commit，体验版本记录的价值
- M5（专题讲解）：git push / status / log，完整工作流
- M6（全链路项目）：全程用 Git 管理，验收时看 commit 历史

**判断标准**：学员在课程结束时，对这些技能的掌握程度应该达到"独立使用"的水平，
而不是"听说过"。


### 内容质量检查

- 每条内容是否有明确对应的学习目标？
- 每条内容是否有明确对应的测评方式？
- 内容是否经过"痛点-惊叫点-爽点"检查？
- **体验层是否按课时落地？**（`course-polish` 已产出润色版；爽点是具体课堂动作而非检查表里的标签）
- **视图分离是否合规？**（学员可见页无情绪曲线 / 无顿悟点与惊叫点编号；开场页未剧透反转）
- 文本量是否匹配预期时长？（通常每分钟 150-200 字口语讲解对应一页课件内容）

## 第二节：实操案例设计模板

### 案例设计原则

1. **场景驱动而非工具驱动**：不是"这个工具有 ABC 功能"，而是"在场景 D 中你应该如何用这个工具"
2. **有决策点**：好的案例在节点上需要学习者做判断，不只是机械执行
3. **真实但脱敏**：基于真实业务场景但做脱敏处理
4. **难度递进**：从"引导式案例"→"半开放式案例"→"完全开放式案例"
> **案例多样性检查**：多个案例之间必须使用不同的需求场景——不要用同一个场景出两个案例。
开场案例、模块练习案例、全链路项目案例应覆盖不同的产品类型
（如 C 端工具 / B 端后台 / 移动端等），确保学员在不同场景下都有练习机会。


### 案例结构

| 要素 | 设计说明 |
|:---|:---|
| **场景描述** | 发生了什么？提供充分的上下文信息 |
| **决策节点** | 需要学习者判断什么？有哪几个可能选项？ |
| **成功标准** | 什么算做对了？什么算做得不够好？ |
| **参考答案** | 给出 2-3 种不同水平的解答，便于讲师做差异化点评 |
| **延展讨论** | 如果场景参数变了，结论是否改变？ |

## 第三节：测评方案设计

### 布卢姆层级与测评形式匹配

| 层级 | 推荐测评形式 | 示例 |
|:---|:---|:---|
| **记忆** | 选择题、判断题、填空题 | "以下哪个是 AI 的常见应用？" |
| **理解** | 简答题、概念图、类比说明 | "用你自己的话解释大语言模型的工作原理" |
| **应用** | 实操题、模拟场景题 | "用 Copilot 为这个需求生成一个高保真原型" |
| **分析** | 案例比较、归因分析 | "分析这两个方案各有什么优劣？为什么？" |
| **评价** | 方案评估、同行评议 | "评估这三份竞品分析报告，哪一份最有效？给出评分和理由" |
| **创造** | 项目产出、设计方案 | "为这个产品需求设计一个完整的 AI 功能方案" |

### PM 课程测评特殊规则
- 判断类能力使用"案例判断 + 同行评议 + 项目产出"替代传统考试
- 每个测评必须附带评分标准，不能只问开放题不评
- 详见 `references/pm-ai-adaption.md`

## 第四节：视觉与交互体验检查

### 课件视觉设计原则

1. **降低认知负荷**
   - 一页只讲一个要点
   - 使用留白和视觉层次（标题>副标题>正文>注释）
   - 避免大段文字（超过 30 字就考虑换图或清单）

2. **信息可视化**
   - 逻辑关系用图表（流程→流程图，对比→表格，因果关系→鱼骨图）
   - 关键数据用可视化（数字不要藏在段落里）

3. **交互设计**（如果是线上课程）
   - 明确的进度提示（当前在哪个模块、还有多久）
   - 可点击的索引/目录
   - 每个交互步骤有即时反馈

### 课程课件内容规范

课件（PPT/可视化材料）是 Phase 03 的第 6 个产出。当课程有多个独立课时时，`05-课程课件/` 是一个**目录**，每课时一个独立课件，不能合并为一个 PPT。

**内容来源规则（v1.3 统一口径）**：课件内容的唯一来源是**四侧材料 + 大纲** —— `00-课程大纲.md`（课次结构）、`01-学员手册.md`（学员阅读文案）、`02-讲师手册.md` 与 `02-讲师手册·润色版.md`（讲师讲解文案）、`03-实操案例.md`（完整示例：好/差对照、逐字稿、数据表）、`04-测评方案.md`（量规与成功标准）。
⛔ `06-课程详细大纲/` 的逐页表是**制作侧中间件**，用于排页序、时长与版式，**不是内容来源**；不得把其单元格按标点切句后直接上屏。
不允许添加上述文件之外的新内容。

> v1.2 及以前本节写「唯一来源是 `02-课程设计方案.md` 和 `01-学员手册.md`」，与同文件「按课时拆分规则」的五源口径冲突，且未声明 `06` 蓝图不得作内容源。v1.3 统一为上述口径，并编译为下方三条硬约束与 Phase 03 完成条件。

### 载体契约（v1.4 硬约束，违反即判不合格）

> 缺陷 **G-9**（第四次实战）：同一 `05-课程课件/` 里 HTML 讲课版与 6 份 PPTX 并存 —— PPTX 仍含旧角色轴「使用者 / 决策者」**20 处**、旧术语「评分作品 / 勾选卡」**10 处**，且无任何代际标注，打开就能上课。**改一处载体 ≠ 改了全部载体。**

**默认载体：HTML 讲课版**（用户 2026-11-08 明确要求：默认输出 HTML，除非特别说明 PPTX）

| 情形 | 产出 | 判据 |
|:---|:---|:---|
| 未提载体 / 只说「课件」「上课用」「能演示」 | **`{课次}-{主题}-讲课版.html`** | 单文件、零外链、双击即全屏演示 |
| 明确说 PPTX / ppt / 幻灯片文件 | `{课次}-{主题}.pptx` | 按按课时拆分规则命名 |
| 两者都要 | 先 HTML，再派生 PPTX | 派生后必须过「口径回归」（判定 4） |

**HTML 讲课版最小技术要求**：单文件零外链（样式与数据内联）；学员视图默认、`?t=1` 切讲师视图；`#页码` 直达；逐页计时器读页级 minutes；生成器从**单一 JSON** 渲染且**零改写文案**（不切句、不删词、不截断）。

**四条判定**：
1. ⛔ 未明确要求即不生成 PPTX；不得以「PPT 更通用」为由自行选载体。
2. 同一课次同一时刻只允许 **1 个可授课载体**；无法删除的另一载体必须显式标 `⛔ 不得授课`。
3. 多载体并存的目录必须有 `05-课程课件/00-课件状态说明.md`（载体 / 状态 / 术语口径 / 依据四列），缺即判不合格。
4. 任一载体内容变更，须对**同课次全部载体**做口径回归；只改一个载体即视为变更未完成（G-9 根因）。

### 成品双视角契约（v1.3 硬约束，违反即判不合格）

> 缺陷 **G-4**（第三次实战）：上屏文案既不是「讲师能照着讲」的讲解稿，也不是「学员能照着读、照着做」的阅读文案，而是第三种「设计/制作视图」的表格单元格残片。107 页 / 364 条上屏要点中，设计目标语 60 条、半截句与硬截断 63 条、13 个内容页零完整可读句。

| 视角 | 唯一合法载体 | 内容要求 | 禁止 |
|:---|:---|:---|:---|
| **① 学员视角（阅读）** | 课件上屏正文 | 完整句子；概念、示例与好/差对照、动作指令、成功标准；脱离讲解也能读懂 | 设计目标语（「这一页结束时…」「完成后应该拿到…」）、制作说明、括号未闭合的半截句、字数硬截断、内部代号、⭐ 标注 |
| **② 讲师视角（讲解）** | 课件**逐页配套的讲解层**（PPT 备注 / HTML 讲师视图 / 逐页讲解卡） | 逐字话术、提问与追问、互动指令、时间提示、常见反应与应急；页锚与课件页序一致 | 只列元数据（课次 / 页码 / 时长 / 要点条数）而无一句可讲话术；把设计视图当讲师视图 |
| **③ 设计 / 制作视图** | `02-课程设计方案.md`、`00` 大纲设计标注、`06` 逐页蓝图、构建脚本与配置 | 排页序、控负荷、标惊叫点、配版式 | ⛔ **任何上屏画面与学员可见文档** |

**三条判定**：
1. 成品只允许前两种视角；设计视图只能作为内部中间件。
2. 任一上屏页必须**同时**具备「学员可读正文」与「逐页讲解层」，缺一即判不合格。
3. 课件生成前必须先产出**逐页双视角文案表**并经用户确认；⛔ 禁止由脚本从 `06` 蓝图反向摘录生成上屏文案。

| 页锚 | 学员视角标题 | 学员阅读文案（上屏） | 来源锚点 | 讲师讲解文案（不上屏） | 来源锚点 | 核心示例完整上屏 |
|:---|:---|:---|:---|:---|:---|:---:|
| 课1 P14 | … | … | `01-学员手册.md` L61-67 | … | `02-讲师手册·润色版.md` L98 | 是 / 否 |

### 学员视角标题契约（v1.3 硬约束）

> 缺陷 **G-5**（第三次实战 + 用户 11-08 举证）：R-1「去剧透」整改把标题从「跃迁：原来我一直在找错东西」压成任务式别名「双视角机会识别」，课件又叠加 `M4 / 75 min / OBJ-04/05`，最终变成索引卡。107 条上屏标题中 **81 条（75.7%）** 命中至少一类标签化问题：内部代号 47 条、`切换 ·` 流程指令 30 条、制作元数据 15 条、名词标签 7 条、短标签词 4 条。**去剧透 ≠ 压成简单词语**。

**合格标题须同时满足 4 条**：
1. **面向学员**：用学员自己的语言，回答「这一页 / 这一节我要解决什么、做完能拿到什么」；允许「我 / 你 / 客户」等主语或明确的待解问题。
2. **完整表达**：是有信息量的短句或「动作：收益」结构；⛔ 禁止名词标签、表名、单个词语（如「字段结构」「两类对象话术对照表」「只评亮点、不排名」）。
3. **无内部代号与制作元数据**：⛔ 上屏标题禁止 `M0 / CASE-1 / S1 / OBJ-01 / D1 / T1 / 30 min / · OBJ / ⭐`；这些只允许留在蓝图与讲师侧。
4. **不剧透但也不空洞**：不含顿悟 / 惊叫点 / 反转结论（如「原来我一直找错东西」），但不得因此退化为标签词；改用**待解问题或动作**表达（如「怎么判断一个机会点该不该做」）。

**正面样板（用户提供，2026-11-08，源自课程大纲「2. 模块清单」主题列）**：

| 合格（学员视角 · 有动作与收益 · 无内部代号） | 不合格（索引卡 / 简单词语） |
|:---|:---|
| 破冰：先把「怕问不到点上」摆到桌面上 | `M0 破冰 · 30 min · OBJ-01 摸底` |
| 开口：分角色访谈，把「想要的功能」问成「实际怎么干活」 | `M1 开口 · 90 min · OBJ-02` |
| 显形：把口述现状画成端到端流程 + 环节画像 | `《流程环节画像表》字段结构` |
| 算账：把「感觉更快」变成客户敢签字的数 | `三档假设 + CASE-1 收益表述好/差` |
| 说服：同一份方案，讲给两种人听 | `切换 · 各写 3 分钟双版本稿` |

> 注：样板中含 ⭐ 的三个惊叫点主题（跃迁 / 重构 / 搭建）**只作设计侧主题名**，上屏须改写为不剧透的待解问题式标题；「去剧透」与「有信息量」须同时满足。
> **切换页标题**：⛔ 禁止以「切换 · 」开头（制作侧流程指令）；改写成对学员的动作指令，如「现在换你：用 5 分钟写下 3 个问题」。

### 术语与口径一致性契约（v1.4 硬约束）

|:---|:---|:---|
| **L1 逐字一致** | 组件名、表头、验收口径 / 合格线、成功标准、物件名 | 与 `01-学员手册.md` 组件表、`04-测评方案.md` 观察表**逐字相同**；⛔ 不得用「分三层」这类描述句替代组件名 |
| **L2 允许白话** | 解释句、课堂提问、讲师口播 | 可换词，但**同一页或相邻页必须有绑定句**（如「可验证事实：能被数字、单据、人名、时间点核对的陈述」绑定「能核对的事实」）；无绑定句即判不一致 |
| **L3 禁止** | 同页混用两种组件名（「三层角色…三类角色」） | 0 处 |

**口径三向核对**（每页必做）：

| 方向 | 核对什么 | 不合格判据 |
|:---|:---|:---|
| ① 页内自洽 | 页内 steps / 分步时长**合计 = 本页 minutes** | 合计 ≠ 页时长（差 1 分钟也算；切换页的 1 分钟须单独计页） |
| ② 分块对齐 | 连续页面之和 = `02-讲师手册.md` 对应时间段分钟数 | 同一动作两处不同时长；上游已承担的段被重复计时 |
| ③ 角色轴互证 | 成功标准要求的覆盖面（如「三类角色都问到」）≤ 该页活动实际给出的角色 / 项数 | 标准要求 3 类、活动只给 2 类（G-8） |

**禁止的做法**：⛔ 为凑页时长把上游已计过的段（示范 / 反馈 / 消化）再列进步骤；⛔ 用「约」「左右」掩盖合计不符；⛔ 用改文案的方式把不合格凑成合格（G-4 教训）。

### 工具卡闭环契约（v1.5 硬约束，违反即判不合格）

> 缺陷 **G-10 / G-11 / G-12**（第五次实战，用户一句「访谈提纲七问是哪七问」挖出）：课件宣称「七问」但上屏是分号串、编号被剥（G-10）；「带四样东西进访谈」里讲师脚本只发 2 件、示范无按卡走的脚本、角色卡对第 5~7 问无答法（G-11）；讲师兜底语「手册附录 A 有卡，翻得到」而附录 A 六张卡里根本没有这张卡（G-12）。**工具有了定义 ≠ 学员拿得到、用得上。**

**每件工具卡必须过五点闭环**（定义 → 发放 → 上屏 → 对手戏 → 实物）：

| 环节 | 落点 | 不合格判据 |
|:---|:---|:---|
| ① 定义 | `01-学员手册.md` 方法组件表 | 组件只在课件出现、手册无定义 |
| ② 发放 | `02-讲师手册.md` 时间轴「发 ×× 卡」动作，写明每人几张 | 组件清单与发放清单数目不一致（如四组件只发两件） |
| ③ 上屏 | 课件页：逐条编号、一条一行 / 一卡一格 | 宣称「N 问 / N 步 / N 张」但上屏是分号串、编号被剥（G-10） |
| ④ 对手戏 | `03-实操案例.md` 角色卡：练习所涉每个问题有答法；答不出的角色写明「换人问」信号 | 学员照卡提问、角色无话可接 |
| ⑤ 实物 | 附录工具卡真实存在，与 ① 逐字一致（允许「同一份内容、以组件表为准」的注明） | 兜底语 / 脚本宣称「附录有卡」而附录无此卡（G-12） |

**三条硬判定**：
1. **数量宣称可数**：凡写「N 问 / N 步 / N 张 / N 轮」的页面，逐条编号数必须等于 N（可用计数校验）；⛔ 不许把编号列表压成分号串。
2. **引用落点可达**：全文（含讲师兜底语、fallback、手册互引）所有「见 X 有 Y / 附录 X 有卡」语句，交付前逐条检索验证；0 命中即 P0。
3. **示范按卡走**：讲师示范段须写明按卡顺序（如 ①→⑦）与标注动作（问完一条划一条）；只写「用手册好例」不算。

| 类型 | 数量 | 内容来源 |
|:---|:---:|:---|

| **学习路径页（学员视图）** | 1 | 从 `00-课程大纲.md` 提取：阶段划分、每阶段学员要交出的产出物、进度感知。**只允许出现「我现在在哪 / 接下来做什么 / 学完能交出什么」** |
| 模块标题页 | 每模块 1 页 | **学员视角标题**（见上方标题契约）、时长；⛔ 不上屏 M 编号 / OBJ 编号 / 惊叫点标注 |

**按课时拆分规则（v1.4）**：
- 每课时一个独立课件文件；**默认 `.html` 讲课版**（见「载体契约」），仅用户明确要求时才产出 `.pptx`

- 每个课时的内容来源 = 该课时的**课程大纲（课时描述）+ 学员手册（对应章节）+ 讲师手册（对应引导）+ 实操案例（引用案例）+ 测评方案（对应ASSESS）**
- 不允许跨课时共用同一页——每个课时的课件独立制作

**质量控制**（对齐检查）：
- 每张课件的 H2/H3 标题 → 能在 `02-课程设计方案.md` 中找到对应模块
- 每张课件的核心观点 → 能在 `01-学员手册.md` 中找到对应段落
- 每个练习页面 → 能在 `03-实操案例.md` 中找到对应案例
- 完成整份课件后 → 对照 `02-课程设计方案.md` 的"学习目标清单"逐条确认每条目标都有对应的课件页

- **每张上屏页的讲解层（v1.3）** → 有逐字话术而非元数据；页锚与课件页序一致
- **核心示例（v1.3）** → 好/差对照、三句改写、逐字稿 100% 完整上屏，不得压缩成结论
- **上屏标题（v1.3）** → 逐条过「学员视角标题契约」4 条判据，标题合格率 = 100%

**视觉质量**（见上方"课件视觉设计原则"）：
- 一页一个要点
- 避免大段文字（超过 30 字换图或清单）
- 关键关系用图表（流程→流程图，对比→表格，因果→图）
- 对齐课程节奏——每 15-20 分钟应有 1 张"切换"页（休息/讨论/实操标识）

## 第五节：敏捷原型验证

### 三个验证节点

| 节点 | 时机 | 验证什么 | 方式 | 耗时 |
|:---|:---|:---|:---|:---|
| **P1** | 分析→设计之间 | 需求假设是否成立？ | 3 个目标学员的 30 分钟访谈 | 2 天 |
| **P2** | 设计→开发之间 | 体验旅程是否有效？结构合理？ | 1 小时最小原型课（PPT+1 个关键练习）+ 2-3 人试听 | 3 天 |
| **P3** | 开发中期（~50% 完成） | 前 20% 内容是否达到预期效果？ | 完整试课 3-5 名目标学员 | 5 天 |

### P3 验证的具体操作

完成约 50% 的内容开发后，执行 P3 验证：
1. 选定课程前 20% 的内容（通常是引言 + 第一个核心模块）
2. 邀请 3-5 名目标学员做一次完整的模拟授课
3. 收集反馈重点：
   - 节奏是否合适？（太快 / 太慢 / 刚好）
   - 认知负荷是否合理？（太多信息 / 太少 / 刚好）
   - 第一个"惊叫点"是否真的产生了效果？
   - 学习者是否理解了课程价值？
4. 根据反馈调整剩余 50% 的内容设计

**2. 启航课微课（录播 15min）**

覆盖所有操作层面的内容：工具注册、GitHub 使用、评审标准、结业条件。学员可反复回看。
