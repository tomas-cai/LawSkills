# 设计阶段参考（Phase 02 - Design）

## 节奏选择

进入本阶段时，先判断用户状态来决定执行节奏：

| 用户特征 | 使用模式 | 做法 |
|:---|:---|:---|
| 消息中包含多个信息点，能一次性回答多个问题 | **批量模式**（默认） | 将下面的核心问题一次性抛出，用户集中回答后统一处理 |
| 消息简短、表示不确定、需要引导 | **逐题模式** | 按下面的探索问题逐个深入追问 |

### 批量模式：核心问题

- 学习目标清单（每条含布卢姆层级的动词 + 可观测成果）
- 模块数量与时长的初步分配
- 测评方式偏好（传统考试/案例判断/项目产出/同行评议）

### 逐题模式：深入探索

- 每个模块的具体活动设计
- 情绪曲线设计（什么模块是高负荷、哪里是休息点）
- 叙事弧的起承转合结构
- 痛点/惊叫点/爽点的逐模块检查

## 第一节：学习目标编写

### 目标编写公式

一个标准的学习目标 = **行为动词 + 内容对象 + 可观测成果**。

**格式**："学员能够[布卢姆层级动词] [内容对象]，[可观测成果]"

**示例**：
- ❌ "学员了解AI工具"（不可观测）
- ✅ "学员能够**区分**AI原型生成工具和AI代码补全工具的**适用场景**，**给出**至少3个选择依据"（分析层，可观测）
- ✅ "学员能够**设计**一个基于AI的前端产品功能，**输出**包含需求说明和原型链接的产品提案"（创造层，可观测）

### 布卢姆层级选择指南

| 期望行为 | 推荐层级 | 典型动词 |
|:---|:---|:---|
| 知道概念/术语 | 记忆 | 列出、识别、命名、复述 |
| 理解原理 | 理解 | 解释、总结、举例、分类 |
| 能用工具操作 | 应用 | 执行、实施、使用、演示 |
| 能判断方案优劣 | 分析 | 区分、组织、归因、比较 |
| 能选择最佳方案 | 评价 | 评估、判断、辩护、推荐 |
| 能创造新方案 | 创造 | 设计、构建、规划、开发 |

### PM 课程的特殊规则

PM 课程的目标往往涉及"判断力"这类非操作类能力。处理方式：
- **判断类能力**：不用"了解/理解/掌握"这类模糊动词，改用"分析/评估/比较/判断/推荐/设计"
- 与其说"学员能理解产品需求优先级"（不可观测），不如说"学员能**评估**三个需求场景的**优先级排序**，**给出**排序依据"
- 详见 `references/pm-ai-adaption.md`

## 第二节：学习体验旅程地图

### 基本思路

像用户体验地图一样设计学习旅程。不是课程大纲（大纲只列知识点），而是**学习者在每个时间切片上的情绪曲线、行为路径和接触点设计**。

### 模板结构

将课程按时间线拆为 3-8 个**核心模块**（不是课时，是体验节点），每个模块包含：

| 维度 | 设计内容 |
|:---|:---|
| **预计时长** | 分钟 |
| **认知层级** | 记忆/理解/应用/分析/评价/创造 |
| **学习目标** | 对应目标编号 |
| **核心活动** | 听讲 / 讨论 / 实操 / 案例分析 / 测评 / 反思 |
| **情绪曲线** | 该模块期望的情绪状态（兴奋/好奇/专注/挑战/成就感） |
| **认知负荷** | 高 / 中 / 低（控制节奏） |
| **关键体验设计** | 痛点解决 / 惊叫点设计 / 爽点营造 |

### 子模块设计（叙事弧模块）

当一个核心教学环节需要"先做→发现→反思→再改进"的设计时，不要压缩在一个模块内。
将这个环节拆为 2-3 个子模块，形成独立的小型叙事弧：

| 子模块 | 功能 | 情绪目标 |
|:---|:---|:---|
| **子模块 A**（如"自由实践"） | 让学员在未受指导的情况下自由尝试，暴露差距 | 好奇→不确定 |
| **子模块 B**（如"揭秘/反思"） | 揭示方法论差距（⭐惊叫点），建立认知冲突 | 认知冲突→"原来如此！" |
| **子模块 C**（如"用方法论重做"） | 用新方法重做同一个任务，验证提升 | 成就感→信心 |

**适用条件**：
- 当某个模块的核心教学策略是"先犯错再教"时 → 拆为子模块 A + B
- 当需要学员对比"旧方法 vs 新方法"的效果差异时 → 拆为 A + B + C
- 如果子模块 C 时间过长（超过 2h），可以考虑独立成一个模块

**节奏控制**：
- 子模块 B（揭秘环节）通常是整节课的情绪高潮，安排在 A 之后立即触发
- 三个子模块的总时长不要超过 4h（超过则意味着需要拆成两个独立模块）
- 每个子模块之间留 2-3 分钟的"思考时间"让学员消化认知冲突



### 情绪曲线设计原则

- 不要全部高负荷（认知疲劳）也不要全部低负荷（无聊）
- 理想节奏：低（热身）→ 高（知识输入）→ 高（认知冲突/惊叫点）→ 中（应用练习）→ 低（反思回顾）
- 每个"高负荷"模块后安排一个"低负荷"模块作为缓冲
- 惊叫点通常在课程中后段，不在开头（需要先建立认知框架才能打破它）

## 第三节：目标-内容-评估对齐矩阵

这是迪克-凯瑞模型的核心校验工具。

### 对齐矩阵

| 学习目标编号 | 目标描述 | 布卢姆层级 | 对应教学内容 | 对应测评方式 | 对齐状态 |
|:---|:---|:---|:---|:---|:---|
| OBJ-01 | ... | 应用 | Module 2 | 实操考核 | ✅ |
| OBJ-02 | ... | 分析 | Module 3-4 | 案例分析 | ❌ 缺测评 |

### 检查规则

1. **无内容的目标**：每条目标是否都有对应的教学内容覆盖？→ 如果没有，目标太宽泛或内容缺失
2. **无测评的内容**：每条教学内容是否都有对应的测评方式？→ 如果没有，学没学到没人知道
3. **层级错配**：目标定在"应用"层，但测评只测"记忆"层？→ 测评设计需要升级

> 对 PM 的判断类课程，高层级测评可用"案例判断 + 同行评议 + 项目产出"替代传统考试题。

## 第四节：叙事弧与认知节奏设计

### 起承转合结构

| 阶段 | 对应的课程环节 | 体验目标 | 时长占比 |
|:---|:---|:---|:---|
| **起** | 开场 → 痛点唤醒 | 建立"为什么学"的紧迫感 | ~10% |
| **承** | 知识构建 → 概念讲解 | 建立认知框架 | ~30% |
| **转** | 认知冲突 → 惊叫点 | 打破旧认知，创造顿悟 | ~20% |
| **合** | 应用检验 → 回顾升华 | 成就感 + 闭环感 | ~40% |

### 认知节奏设计要点

1. **每个模块有明确"信息量"上限**：一次只讲 3-5 个新概念，超过就是认知过载
2. **每 15-20 分钟切换一次学习活动**：讲→练→讨论→讲→练
3. **留白时间**：每 45 分钟课程至少留 5 分钟给学习者消化和提问
4. **前置知识检查**：在讲新概念前先确认学习者的先决知识是否到位

## 第五节：痛点/惊叫点/爽点设计检查表

### 定义回顾

| 概念 | 定义 | 课程场景示例 |
|:---|:---|:---|
| **痛点** | 学习者在学习前/学习中遇到的真实困难、焦虑、挫败 | 担心学不会、觉得跟实际工作无关、基础断层跟不上 |
| **惊叫点** | 让学习者发出"原来如此！"的顿悟时刻 | 一个反转案例、一个颠覆常识的原理揭示、一次"我竟然也能做出来"的实操收获 |
| **爽点** | 让学习过程顺畅、有掌控感的细节体验 | 恰到好处的提示、即时的正向反馈、清晰的进度感知、美观易用的课件 |

### 逐模块检查

| 检查项 | 模块1 | 模块2 | 模块3 | ... |
|:---|:---|:---|:---|:---|
| **痛点解决**：本模块解决了学习者的什么具体痛点？ | | | | |
| **惊叫点设计**：学习者会在哪一个环节产生"原来如此"的感觉？ | | | | |
| **爽点营造**：本模块在体验细节上做了什么让学习顺畅的设计？ | | | | |
| **认知负荷合理**：本模块的学习强度是否适当？ | | | | |

## 第六节：阶段归属矩阵（结构层硬门禁，v1.6 新增）

### 为什么需要这一节

2026-11-08 真实事故（缺陷 **G-14**）：一门名为「AI 落地端到端实战：**场景梳理 · 方案设计 · 智能体实施**」的课，被压成「前 3 天学完全部方法、后 2 天拿真客户跑全案」。时间账 3 × 270 = 810 分毫不差，但后两天做的四件事（访谈、画像、机会识别、重画流程）**全部属于前两个阶段**，且前三天已用同样素材各做过一遍。后果：① 与课程名第三段错位；② 学员经历「已通关又要重来」的二次启动；③ 真正该吃重的「实施」段只占 1/3。

**根因不在算术，在缺一张表**：分钟合计相等被当成了结构正确；每个活动「属于哪个阶段」从未被显式标注过。

> **核心判据：分钟账合计相等 ≠ 分段归属正确。过算术闸不能推出过语义闸。**

### 三条硬规则

| # | 规则 | 具体做法 | 判定（可机械执行） |
|:---:|:---|:---|:---|
| **R-1** | **课名即结构** | 把课程名按 `·` / `：` 拆成阶段清单（如「场景梳理 / 方案设计 / 智能体实施」＝3 段）；每个授课单元（天 / 课次 / 半天）**必须标称恰好一个阶段** | 单元标称阶段数 = 1；单元内出现其他阶段的活动 → **结构错误** |
| **R-2** | **阶段归属矩阵** | 任何排期定稿前，逐条列出 `活动 → 所属模块 → 所属阶段`，三列齐备后才能进时间校验。模板见下 | 矩阵缺行 / 有活动查不到所属阶段 → 不得定稿 |
| **R-3** | **新增单元三问** | 新增一个单元（天 / 课次 / 半天）前必答：① 这个单元练的是哪个阶段的能力？② 这个动作前面做过吗、做过几次？③ 若重做，第三遍的**增量**是什么？ | ③ 答不出「增量」→ 判**伪新增**，删除或改为深化（换环境 / 换数据 / 换角色，不换任务类型） |

### 配套两条

| # | 规则 | 说明 |
|:---:|:---|:---|
| **R-4** | **时长依权重，不得均分** | 每段时长须给出依据（能力权重 × 实践占比），⛔ 不得因「看起来整齐」默认均分。缺陷 **G-15**：三段各 270 min 的三等分，让「实施」这种最该动手的段只拿 1/3，而课程名把它列为第三段 |
| **R-5** | **深化 ≠ 重做** | 同一课题跨单元复用时，**只能改三样**：环境真实度（干净→脏→真）、输入质量、学员角色（搭建者→加固者→推动者）。⛔ 不得改任务类型（访谈→画像→机会→流程 这类跨阶段推进就是重做） |

### 阶段归属矩阵模板

```markdown
| 单元 | 活动 | 所属模块 | 所属阶段 | 与课名第几段对应 | 前面做过吗（次数） | 本单元增量 |
|:---|:---|:---|:---|:---:|:---:|:---|
| D4 | 客户方案确认会（20 min 追问） | 承 D2 的《待客户确认》清单 | 智能体实施 | 第 3 段 | 否（D1 是练开口，非补事实） | 清单清零 |
| D4 | ~~访谈~~ | ~~M1~~ | ~~场景梳理~~ | 第 1 段 | 是（D1 已做） | 无 → **删除** |
```

> 矩阵里出现「所属阶段 ≠ 单元标称阶段」的行，只有两个合法出口：**移到对应阶段的单元里**，或**改成该阶段的深化动作**。⛔ 不允许「反正时间够，加进来」。

### 设计阶段检查项（阶段收尾必答）

1. 课程名拆出几个阶段？每个阶段对应哪个单元？有没有阶段没有任何单元承载？
2. 每个单元的标称阶段是不是恰好 1 个？矩阵里有没有跨阶段行？
3. 有没有「同一任务类型出现两次以上」的单元？第三遍的增量写清了吗？
4. 每段时长的依据是什么？是不是默认均分了？
5. 按「实施 / 落地 / 交付」命名的那一段，它占的时长配得上课程名给它的位置吗？

## 第七节：结构模式选择（阳性方法，v1.7 新增 · v1.8 标层级）

第六节是**阴性规则**（不准跨阶段、不准均分、不准重做）；本节是**阳性方法**（那到底该选哪种结构）。

> ⚠️ **先定层级再用本节（v1.8）**：本节处理的是 **L2 培训项目架构**（几天 / 几门课 / 实战配比 / 客户到场日），**不是** L3 一门课内部的模块顺序。层级定义与「课程 / 课程体系 / 培训项目 / 课次」的叫法边界见 → `structure-levels.md`。⛔ **用 L3 的课程阶段去填 L2 的项目天数，是本类错误的共同起点**。
>
> 完整方法论见 → `program-structure.md`（六道闸理论栈 / 三张前置卡 / 五种模式 / 选择矩阵 / 8 条反模式 / 回接技术）。
> 本节只留定稿必用的最小集。

### 定稿前必须落字的三张卡

| 卡 | 关键字段 | 缺了会怎样 |
|:---|:---|:---|
| **出口绩效卡** | 可交付产出物 / 完成条件 / ≥3 条可观测判据 / 谁验收 / 独立度等级（观察→监督下→独立→能教） | 目标退化为「了解 / 掌握」，后面全空转 |
| **任务清单卡** | 任务 × 频率 × 关键性 × 难度 × **是否可培训** | 把「无权限、无接口」的任务排进课堂，做也落不了地 |
| **学员起点卡** | 已会什么 / ≥3 条常见错误概念 / 班内最大差距 | 老手被当新手（专长逆转），新手被当老手（支架不足） |

**任一张为空 → 方案首页必须标「假设版结构」并写明缺哪张、谁补、何时补。⛔ 不得宣称最佳实践。**

### 模式选择（按序判别，第一个「是」即为推荐）

| 序 | 判别问题 | 是 → |
|:---:|:---|:---|
| Q1 | 学员起点差异极大？ | 先分层再选模式 |
| Q2 | 出口绩效是**单一**复杂技能？ | **P3 案例阶梯** |
| Q3 | 各阶段产出物**彼此独立可用**？ | **P1 阶段块状**（合法） |
| Q4 | 有真实客户/交付物且周期允许间断？ | **P4 项目主线** |
| Q5 | 集中 ≤5 天且迁移要求高？ | **P2 整体任务螺旋**（默认） |

> ⛔ **「成果物强链式」是 P1 误用的总根源**：正因为后段依赖前段，才更该让学员尽早见全貌，而不是更晚。答不出 Q3 的「是」就不许用 P1。

### 回接（零增时修「全案后置」）

若必须用 P1 或链条强耦合：把每个单元**已有的收尾/评议时段**改成「接回整条链——现在就要交付，还缺什么」，并让讲师用 15 min 演示极简全链。**不新增分钟，只改内容**。
判定：单元结束时学员能否说出「我这件东西在整条链哪一环、下一步谁接」。

### 设计阶段检查项（v1.7 追加，与第六节 5 问合并使用）

6. 选的哪个模式？**判别矩阵哪一问给的答案**？（写不出 → 无依据，退回重选）
7. 学员第一次见到完整链路在第几个单元？若是最后一个 → 反模式 A-1，必须加回接。
8. 课后 4 周内，学员是否至少有 3 次「被要求用」的机会？（无 → 缺 6Ds D4，迁移率会掉到个位数）

### 课时主题命名

当课程被设计为多个独立课时（如翻转课堂的多次直播课）时，每个课时应该有一个**主题名称**，而不是编号。

**原则**：主题名称是对学员说的，不是对教务说的。学员看到"课 3：文档：AI 产品需求的语言"就知道这节课要学什么；看到"课 3"只会想"上节课讲了什么来着？"

**命名方法**：用一个动词 + 一个名词的组合，描述学员在这节课的**认知转变**。

| 课时 | 课程序号 | 有主题的版本 |
|:---|:---|:---|
| 第一节课 | 课 1 | **体验**：对话驱动的力量与局限 |
| 核心转折点 | 课 2 | **跃迁**：从对话驱动到规范驱动 |
| 工具/方法课 | 课 3 | **文档**：AI 产品需求的语言 |
| 项目启动 | 课 4 | **起跑**：全链路项目启动 |
| 最后打磨 | 课 5 | **打磨**：交互设计与终期冲刺 |
| 毕业展示 | 课 6 | **绽放**：毕业展示与复盘 |

将主题名称写入 `00-课程大纲.md` 和 `02-讲师手册.md` 的课时标题中。
