## 布卢姆行为动词手册

### 完整动词表

| 层级 | 常用动词 | PM 课程推荐动词 | 不推荐（太模糊） |
|:---|:---|:---|:---|
| **记忆** | 列出、识别、命名、复述、定义 | 列举、识别 | 了解、熟悉 |
| **理解** | 解释、总结、举例、分类、推断 | 解释、总结、类比 | 理解、掌握 |
| **应用** | 执行、实施、使用、演示、操作 | 使用、制作、演示 | 运用 |
| **分析** | 区分、组织、归因、比较、拆解 | 比较、分析、拆解 | 分析清楚 |
| **评价** | 评估、判断、辩护、推荐、排序 | 评估、判断、推荐 | 评价 |
| **创造** | 设计、构建、规划、开发、制定 | 设计、规划、提出方案 | 创新 |

### 动词选择原则

1. 动词必须**可观测**——别人能看到学员完成了这个动作
2. 动词必须**可测评**——有人能用评分标准评价完成质量
3. 优先用**具体动词**避免**抽象动词**
   - ❌ "学员能理解用户需求"（理解不可直接观测）
   - ✅ "学员能**列出**至少 5 种用户需求分析方法，并**选择**一种**设计**一份访谈提纲"（三个具体行为可观测）

## 敏捷验证节点模板

### P1 验证（分析→设计之间）

验证问题：
- 学员是否真的有这个痛点？痛到什么程度？
- 学员对课程主题的预期是什么？
- 我们设计的解决方案方向是否对？

操作：
- 找 3 个目标学员做 30 分钟访谈
- 不需要任何教学内容，只需要一个课程概述（1 页纸）

### P2 验证（设计→开发之间）

验证问题：
- 课程结构是否合理？模块之间逻辑是否自然？
- 体验旅程是否有效？情绪曲线是否合理？
- 第一个"惊叫点"设计是否有效？
- **开场页是否剧透了惊叫点？情绪曲线是否仍留在设计视图、未做成学员可见页？（v1.1 新增）**
- **体验层是否已有按课时的话术与节奏动作，而不只是 Phase 02 的检查表？（v1.1 新增）**
- **规范整改后是否已做全包回归检索，而不是只改被举证的那一页？（v1.2 新增）**

操作：
- 准备 1 小时的最小原型课程（PPT + 一个关键练习）
- 找 2-3 人做一次试讲
- 收集反馈后调整设计

### P3 验证（开发中期~50%）

验证问题：
- 前 20% 的内容是否达到了预期学习效果？
- 节奏和认知负荷是否合理？
- 是否有需要大规模调整的地方？

操作：
- 用已开发的前 20% 内容做一次完整试课
- 3-5 名目标学员
- 收集反馈，决定剩余 50% 是否需要调整方向

> 以下五个维度构成比检查清单更全面的评审模型。建议在每个课程项目交付后按顺序执行。

### 1. 结构完整性检查

验证产出物流是否完整，每个阶段的产出物是否存在：

| 检查 | 标准 |
|:---|:---|
| 00-* | 如执行过 Phase 00，`00-*.md` 应存在，含信号摘要和课程假设 |
| 01-* | `01-*.md` 应存在，含需求来源、痛点验证、学习者画像、能力差距 |
| 02-* | `02-*.md` 应存在，含学习目标、情绪曲线、对齐矩阵 |
| 03-*/ | `03-*/` 应存在，含课程大纲、学员手册、讲师手册、实操案例、测评方案 |
| 04-* | `04-*.md` 应存在，含前置测评、随堂验证设计 |
| 05-* | `05-*.md` 应存在，含柯氏评估、迭代计划 |
| 每个产出物的"本阶段完成检查" | 检查项应为已勾选状态（[x]），未勾选的需说明原因 |

### 2. 内部一致性检查

验证跨阶段的信息是否一致，这是最容易出现断裂的地方：

| 检查项 | 对应关系 | 典型断裂 |
|:---|:---|:---|
| 目标人群 | Phase 01 画像 → Phase 02 目标 → Phase 03 案例 → Phase 04 前置测评 | 画像写的是"零经验毕业生"，但案例假设了 2 年工作经验 |
| 学习目标 | Phase 02 目标 → Phase 03 测评 → Phase 05 达成度 | OBJ 在 Phase 02 定义了，但在 Phase 03 没有对应的测评 |
| 情绪基线 | Phase 01 情绪 → Phase 02 情绪曲线 → Phase 03 讲师话术 | Phase 01 说"焦虑"，但讲师手册没有针对焦虑设计话术 |
| 痛点假设 | Phase 00/01 痛点 → Phase 05 痛点复盘 | Phase 05 复盘的问题在 Phase 01 没有定义过 |

**检查方法**：挑三个关键字段（目标人群 / 核心痛点 / 课程目标），从 Phase 01 开始沿着产出物流往下看，每到一个阶段停下来确认"这个阶段的文件是否还认同一个字段"。

### 3. 内容深度检查

比"文件存在"更进一步——文件的内容是否达到了"可教学"的质量：

| 深度层级 | 定义 | 检查方法 |
|:---|:---|:---|
| **L1** 骨架级 | 有文件，有结构，有占位符 | 文件能打开 |
| **L2** 填充级 | 内容完整，可读性强 | 逐段阅读，没有"待填写"标记 |
| **L3** 教学级 | 拿到就能上课，讲师不需要额外准备 | 模拟一节课——只读手册，能讲吗？ |
| **L4** 精品级 | 有视觉设计、有录屏、有课后扩展 | 学员体验完整，超出预期 |

**目标**：课程交付时至少达到 L2（填充级），关键模块（如第 1 天的第 1 个模块）应达到 L3（教学级）。

### 4. 可教性检查

模拟"明天就要上课"场景，验证材料是否可执行：

| 检查项 | 操作方式 |
|:---|:---|
| 1. 时间表是否可执行 | 把 00-课程大纲.md 的每段时间加起来，看是否等于总时长 |
| 2. 讲师能否照着讲 | 打开讲师手册，从 M1 到结束，逐段读一遍——"这里有盲区吗？" |
| 3. 案例是否可操作 | 还原案例场景，确认决策点有明确选项，参考答案有差异层次 |
| 4. 测评是否可评分 | 拿学员的 3 份不同水平作业试评，看评分标准能否区分出优/中/差 |
| 5. 技术依赖是否确认 | 实操环节用到的工具/平台/API 是否都已确认可运行 |

### 5. 风险评估

识别课程交付前最可能出问题的 3 件事：

```
风险 1：[如"M4-1 自由手搓依赖 AI 工具可用性"]
  影响：如果 Cursor 不可用，整个 M4 叙事弧断裂
  概率：低
  应对：准备本地演示录像作为降级方案

风险 2：[..."...."]
  影响：...
  概率：...
  应对：...
```

**风险来源**：讲师经验（没讲过的环节）、技术依赖（AI 工具、API）、学员差异（跨度大的分层）、内容时效性（过时的案例）。

---

> **项目交付审阅已独立为  Skill**：如需对课程项目做结构化评审（结构完整性、内部一致性、内容深度、可教性、风险评估），请使用 course-review Skill，不再通过 course-design 调用。

### 规范变更后的全包回归检索（v1.2 硬约束）

> **触发条件**（任一命中即须执行）：① 专家包规范修订（视图分离 / 体验层 / 编号契约 / 术语口径）；② 任一已产出文件因评审意见被整改；③ 修改了被其他文件引用的小节名、页面名、物件名或术语。
> **禁止**：只改「被举证的那一页 / 那一处」。第二次实战中，仅改课1 页 2 而使设计视图从 4 个不同入口漏进学员材料；改用扩展词表做全包回归后，又查出 4 类原评审未点名的残留（半天总结页旧口径、失效来源锚点、逐页区 ⭐ 编号、自检的过度断言）。

| 检索范围 | 具体位置 | 合格判据 |
|:---|:---|:---|

**正向内容验收（v1.3 新增；⛔ 验收不得只跑负向词表）**：除三类判定外，须另跑下表 7 项结构判据并留下分布记录。

| 判据 | 计算方法 | 合格线 |
|:---|:---|:---|
| 完整可读句率 | 上屏要点中「无制作侧词 + 长度 ≥12 + 无残缺」的条数 / 总条数 | ≥ 90%，且逐页 ≥1 条 |
| 半截句 / 括号未闭合 / 硬截断数 | 正则检 `（[^）]*$`、`[+＋/(（／→、]\s*$`、`…$` | 0 |

**验收记录（须写进项目 `VERSION.md` 或评审报告）**：
1. 检索文件数、词表版本、每类命中数及归类；
2. **禁止以「其余 N 章未变」代替全包检索结论**——该类断言只在完成全包检索后才可写；

## 术语与口径一致性工具（v1.4 新增）

> 触发：任一课件 / 教学材料发生术语、物件名、验收口径、页时长变更，或交付前评审。
> 依据：缺陷 **G-6 / G-7 / G-8 / G-9**——视角契约（1.3）解决「写给谁」，本节解决「同一样东西是不是只有一种叫法、一处时长」。

### 1. 术语单一真源表（每条课程必建，放在 `06-课程详细大纲/` 或 `03-教学材料包/`）

| 字段 | 取值来源（唯一） | 例 |
|:---|:---|:---|
| 组件名 | `01-学员手册.md` 该模块「方法组件」表第一列 | 三类角色 / 破冰话术卡 / 访谈提纲 / 可验证事实 |
| 表头与量规名 | `04-测评方案.md` 观察表 / 量规表首列 | 三类角色覆盖 / 可验证事实条数 |
| 验收口径 | `01` 每章「验收线」+ `04` 量规合格档 | ≥5 条可验证事实；出现未转换的功能词即未达标 |
| 物件名 | `01` 分步实操中出现的实体名 | 恐惧点勾选卡 / 角色卡（4 张） |
| 角色轴 | `02-课程设计方案.md` 现行版本 | 老板（决策层）/ 主管（管理层）/ 一线（执行层） |

⛔ 真源只能有一个。若 `01` 与 `04` 冲突，先修 `01`+`04` 再改下游，不得在课件里二选一。

### 2. 术语三级判定（逐页过）

| 级别 | 合格线 | 不合格样例 |
|:---|:---|:---|
| L1 逐字一致 | 组件名 / 表头 / 验收口径 / 成功标准 / 物件名 与真源**逐字相同** | 真源「三类角色」→ 课件写「三层角色」 |
| L2 白话绑定 | 允许换词，但同页或相邻页有**绑定句**把术语与白话连起来 | 课件写「能核对的事实」而全课无一处把它绑到「可验证事实」 |
| L3 同页禁止混用 | 同一页内同一概念只有一种叫法 | 同页既写「三层角色」又写「三类角色都问到」 |

**扫描口径**（可用 `grep -c` / python 精确计数，⛔ 不用近似匹配）：
1. 逐个术语在**全部载体**（md / html / pptx XML）计数，输出「文件 × 术语 × 次数」矩阵；
2. 命中 ≠ 违规：先按 L1/L2/L3 分级，再判定（历史 Changelog 行、需求原话留痕、通用语义不计）；
3. 判定结果写进评审报告，禁止只写「已检查」。

### 3. 口径三向核对（逐页过）

| 方向 | 算法 | 常见错法 |
|:---|:---|:---|
| 页内自洽 | `sum(页内 steps 分钟) == 页 minutes` | 4 步 5/15/30/10=60，页面写 27 |
| 分块对齐 | 相邻页 minutes 之和 == 讲师手册时间段（如 35-65 = 30） | 把示范 15、反馈 15 又列进实操页步骤 |
| 角色轴互证 | 成功标准要求的覆盖面 ≤ 该页活动给出的项数 | 3 轮却只排 2 类角色，标准要求 3 类 |

**根因提示**：重复计时多半来自「把上游页已承担的段落又抄进本页步骤」。改法只有一条 —— 删重复段，不是改数字。

### 4. 载体代际清点（改完必跑）

```bash
# 1) 目录里到底有几个载体
ls -la 03-教学材料包/05-课程课件/
# 2) 每个载体的旧术语残留（md 与 html 直接 grep；pptx 需解压 slide XML）
# 3) 缺 00-课件状态说明.md 且载体 >1 → 判不合格
```

判定：同课次只允许 **1 个可授课载体**；其余必须标 `⛔ 不得授课` 并写明旧口径残留数。`术语 0 残留 ≠ 内容可用`（旧代产物即使 0 残留也不能上课）。


## 工具卡闭环工具（v1.5 新增）

> 触发：任一课件 / 手册出现「N 问 / N 步 / N 张卡」类数量宣称，或引用「附录 / 手册 / 案例里有 ××」。
> 依据：缺陷 **G-10 / G-11 / G-12**——口径契约（1.4）管「一种叫法」，本节管「一件工具从定义到学员手上是否断链」。

### 1. 工具卡五点清点矩阵（每条工具卡一行）

| 工具卡 | ①定义(01) | ②发放(02) | ③上屏可数 | ④对手戏(03) | ⑤实物(附录) |
|:---|:---:|:---:|:---:|:---:|:---:|
| （逐卡过，任一格 ✗ 即 P1；⑤宣称有而实际无 → P0） | | | | | |

**扫描口径**：对每张卡名做「文件 × 载体」计数矩阵；`02` 中发卡清单与 `01` 组件清单数目必须相等；宣称「N 条」的列表逐条编号并计数相等。

### 2. 引用落点校验（交付前必跑）

```bash
# 抽出所有「见/详见/附录/手册 …有/见」句 → 逐条在目标文件检索关键词 → 0 命中即 P0
```

⛔ 兜底语（讲师 fallback）里的落点同样要验——课堂上让学员翻一本翻不到的手册，比没有兜底更伤可信度。

### 3. 示范脚本检查

讲师示范段须含：按卡顺序（①→⑦）+ 每步标注动作（问完一条划一条 / 标出拿到哪类事实）。缺失即 P1。


## 阶段归属检查工具（v1.6）

> 用于**课程结构 / 排期方案**定稿前。判据与判定见 `phase-02-design.md` →「第六节 阶段归属矩阵」。

### 工具 1：课名拆段表

| 课程名 | 分隔符 | 拆出阶段 | 阶段数 | 每段对应的授课单元 | 有单元承载？ |
|:---|:---:|:---|:---:|:---|:---:|
| （填入完整课名） | `·` / `：` | 段 1 / 段 2 / 段 3 | 3 | D1 / D2 / D3-D5 | ✅ / ❌ |

**判据**：每个阶段至少 1 个单元承载；有阶段无单元 → 结构缺口（P0）。

### 工具 2：归属矩阵（三列齐备才可定稿）

| 单元 | 活动 | 所属模块 | 所属阶段 | 课名第几段 | 前面做过吗（几次） | 本单元增量 | 判定 |
|:---|:---|:---|:---|:---:|:---:|:---|:---:|
| | | | | | | | ✅ / ⛔ 跨阶段 / ⛔ 伪新增 |

**三条判据**
1. **跨阶段**：`所属阶段 ≠ 单元标称阶段` → 只有两个出口：移到对应单元，或改成该阶段的深化动作；⛔ 不允许「时间够就加」。
2. **伪新增**：同一任务类型出现 ≥2 次，且「本单元增量」栏为空 → 删除或改为「换环境 / 换数据 / 换学员角色」的深化。
3. **时长均分**：每段时长填「依据」栏（能力权重 × 实践占比）；N 段时长完全相等且无依据 → 判均分（G-15）。

### 工具 3：伪新增三问（每个新增单元必答）

| # | 问题 | 不合格答案特征 |
|:---:|:---|:---|
| 1 | 这个单元练的是哪个阶段的能力？ | 答「综合练习」「全流程走一遍」= 没有阶段 |
| 2 | 这个动作前面做过吗、做过几次？ | 答不出次数 = 没查过 |
| 3 | 若重做，第三遍的**增量**是什么？ | 答「更熟练」「巩固」= 伪新增 |

### 阶段归属检查（设计阶段收尾 / 评审时各跑一次）

- [ ] 课名拆段表已产出，每段有单元承载
- [ ] 归属矩阵三列齐备，**跨阶段行 0**
- [ ] 每个重复任务类型都有增量说明，**伪新增 0**
- [ ] 每段时长有依据，**均分 0**
- [ ] 按「实施 / 落地 / 交付」命名的那一段，时长与它在课名中的位置相称
