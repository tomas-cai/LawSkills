# 磨课 (Course Design) Skill

## 核心理念

**把课程当作产品做**。学习者就是用户，教学就是体验设计，而不仅是知识传递。

## 项目结构与产出物流

Skill 的核心设计：**每个阶段产出唯一的标准化文件，下一阶段以此为输入**。这类似 superpowers——每个技能独立可调用，产出物是阶段间的契约。

```
<course-project-root>/             ← 课程项目根目录（用户指定）
│
├── 00-培训需求spec.md            ← 来自 course-discovery → Phase 01 读取
├── 01-需求定位报告.md            ← Phase 1 产出 → Phase 2 读取
├── 02-课程设计方案.md            ← Phase 2 产出 → Phase 3 读取
├── 03-教学材料包/                ← Phase 3 产出（目录）→ Phase 4 读取
│   ├── 00-课程大纲.md
│   ├── 01-学员手册.md
│   ├── 02-讲师手册.md
│   ├── 03-实操案例.md
│   ├── 04-测评方案.md
│   ├── 05-课程课件/              ← 视觉出版物（每课时一个独立课件；**默认 HTML 讲课版**，PPTX 仅在明确要求时）
│   └── 06-课程详细大纲/          ← 逐页内容蓝图，用户审查确认后再进入 05 视觉制作
├── 04-实施记录与反馈.md          ← Phase 4 产出 → Phase 5 读取
├── 05-评估报告与迭代计划.md      ← Phase 5 产出（完结）
└── 06-微课补充包/                ← 可选扩展位，本专家包暂未提供微课技能
```

### 产出物契约

每个产出物是自包含文件（或目录），含两部分：
1. **元数据头**（结构化摘要：课程名、阶段、完成日期）
2. **内容正文**（本阶段完整产出）

产出物的具体格式由各阶段参考文件中的"产出物结构"章节定义。

> **v1.3 附产物**：`06-课程详细大纲/逐页双视角文案表.md` 是 `05-课程课件/` 的**强制前置产物**，不新增主编号（归在 `06` 下）；课件不得越过它直接从蓝图生成。见 `references/phase-03-development.md` →「成品双视角契约」。
> **v1.4 载体与口径**：`05-课程课件/` 的**默认载体是 HTML 讲课版**（单文件、零外链），⛔ 用户未明确说 PPTX 时不得生成 PPTX；同一课次只允许 1 个可授课载体，多载体并存须有 `00-课件状态说明.md`。术语 / 页时长 / 角色轴须过「术语与口径一致性契约」。见 `references/phase-03-development.md` →「载体契约」「术语与口径一致性契约」。

## 入口与阶段选择

当用户提出课程开发需求时：

1. **已有课程项目** → 询问项目目录路径，检出已有产出物判断进度
2. **新课程项目** → 询问存放路径 + 课程基本信息，从分析阶段开始
3. **指定中间阶段**（如"我已有需求分析报告"）→ 读取用户提供的文件 → 从对应阶段开始

### 进度判定规则

```
检出 00-培训需求spec.md → 不存在 → 告知用户：可用 course-discovery Skill 做需求探索，或直接开始 Phase 01
检出 00-培训需求spec.md → 存在 → 自动读取作为 Phase 01 输入

检出 01-需求定位报告.md → 不存在(且无00) → 从 Phase 01 开始
检出 01-需求定位报告.md → 存在   → 问用户是否继续 Phase 02
检出 02-课程设计方案.md → 存在   → 问用户是否继续 Phase 03
检出 03-教学材料包/    → 存在   → 问用户是否继续 Phase 04
检出 04-实施记录与反馈.md → 存在  → 问用户是否继续 Phase 05
检出 05-评估报告与迭代计划.md → 存在 → 课程已完成，问是否开新课或迭代
```

**原则**：不让用户一开始就定义所有细节——设计的价值在分析中逐步收敛。也不强迫用户从头开始——已有产出物应该复用。

## 阶段执行节奏

每个阶段有两种执行模式，进入阶段时自动判断。判断依据：进入阶段时用户的消息风格。

| 用户特征 | 使用模式 | 做法 |
|:---|:---|:---|
| 消息中包含多个信息点，能一次性回答多个问题 | **批量模式**（默认） | 将参考文件中的"核心问题"一次性抛出，用户集中回答后统一处理 |
| 消息简短、表示不确定、或被问到才知道 | **逐题模式** | 按参考文件中的"探索问题"逐个深入追问 |

各阶段的"核心问题"和"探索问题"定义在该阶段 reference 文件头部的"节奏选择"章节。

## 理论基础（概述）

**六维嵌套模型**：六层**不是六个按顺序执行的步骤**，而是同时压在**同一份课程产物**上的六个检查视角——「嵌套」指多视角共同作用于同一产物。首次使用时读 `references/overview.md` 建立心智模型；**每个阶段收尾用六层各照一遍**；交付前由 `course-review` 把关。

| 层次 | 维度 | 解决的问题 | 每阶段收尾的体检动作 |
|:---|:---|:---|:---|
| **流程层** | ADDIE | 项目管控 | 本阶段产出物是否落盘、能否被下一阶段读取 |
| **质量层** | 迪克-凯瑞 | 内容对齐 | 目标 → 内容 → 测评是否逐条对齐；**v1.6 加做结构对齐：阶段 → 单元归属矩阵是否无跨阶段行** |
| **精度层** | 布卢姆 | 目标精度 | 能力差距与目标动词层级是否匹配业务期望 |
| **体验层** | LXD + 产品思维 | 学习动机与完课率 | 情绪基线 → 旅程地图 → 按课时话术/节奏 → 随堂验证，四段是否都落地；**v1.3 加做成品双视角体检：每页是否学员可读 + 讲师可讲 + 标题面向学员** |
| **敏捷层** | SAM/AGILE | 内容时效性 | P1/P2/P3 门禁状态；内容稳定性分层是否标注 |
| **评估层** | 柯氏四级 | 效果闭环 | L1-L4 与痛点假设复盘是否已有采集设计 |

### 体验层三个抓手（作用域必须区分）

| 概念 | 定义 | 作用域 | 承载位置 |
|:---|:---|:---|:---|
| **痛点** | 学习者的真实困难与焦虑 | 跨两层：① **需求事实**（Phase 01 学员画像的情绪基线）② **教学动作**（开场痛点唤醒） | Phase 01 分析 / Phase 02-03 开场 |
| **惊叫点** | "原来如此！"的顿悟时刻 | **模块 / 子模块级事件**：A 自由做 → B 反转揭秘 → C 重做 | Phase 02 定位 / Phase 03 逐页触发 / `course-polish` 按课时兑现 |
| **爽点** | 顺畅有掌控感的细节体验 | **分钟级细节**：提示卡、即时反馈、进度感知、课件可读性、节奏切换 | Phase 03 开发 / `course-polish` 按课时兑现 / Phase 04 验证 |

**术语统一（v1.1）**：本专家包只用「痛点 / 惊叫点 / 爽点」三个词；**不引入「痒点」「尖叫点」等外部说法**；「认知高潮 / 情绪高潮 / 顿悟」仅作描述，不作为可引用的设计对象名。

> **体验层硬规则（v1.1 新增，违反即判不合格）**
> 1. **惊叫点的位置与内容不得在开场页向学员预告** —— 反转须先建立认知框架再打破，提前公示会稀释顿悟。
> 2. **情绪曲线是设计视图**，写在 `02-课程设计方案.md` 与讲师手册附录、标「设计视图·不上屏」，**不得直接做成学员可见课件页**；学员视图只给阶段、产出物与进度感知。
> 3. **体验层须由 `course-polish` 按课时落到话术与节奏**；只有 Phase 02 的曲线与检查表，不算体验层完成。
> 4. **成品只允许学员视角与讲师视角（v1.3 新增）**：课件上屏正文须「学员能照着读、照着做」，逐页讲解层须「讲师能照着讲」；设计 / 制作视图只能作内部中间件。⛔ 禁止把蓝图单元格、预期效果列、制作说明、内部代号搬上屏；⛔ 禁止把「讲师视图」做成元数据面板。见 `references/phase-03-development.md` →「成品双视角契约」与「学员视角标题契约」。
> 5. **同一件东西只有一种叫法、一处时长、一个载体（v1.4 新增）**：组件名 / 表头 / 验收口径须与 `01` `04` **逐字一致**；页内步骤时长合计须等于页时长且对齐讲师手册分钟轴；同一课次只允许 1 个可授课载体。⛔ 不得为凑判据改文案，也不得「改一个载体就算改完」。见同文件 →「术语与口径一致性契约」「载体契约」。
> 6. **每件工具卡必须能走完五点闭环（v1.5 新增）**：定义（`01` 组件表）→ 发放（`02` 时间轴）→ 上屏可数（逐条编号 = 宣称数）→ 对手戏（`03` 角色卡有答法）→ 实物（附录卡真实存在）。⛔ 数量宣称不许压成分号串；「见 X 有 Y」须逐条验证可达，讲师兜底语同样受检。见同文件 →「工具卡闭环契约」。
> 7. **课名即结构，单元不得跨阶段（v1.6 新增）**：把课程名按 `·` 拆成阶段清单，每个授课单元（天 / 课次 / 半天）**只标称一个阶段**，单元内不得出现其他阶段的活动。⛔ **分钟合计相等 ≠ 分段归属正确**——时间账过闸不能推出结构过闸。新增单元前必答三问（练哪个阶段 / 前面做过几次 / 第三遍的增量是什么），答不出增量即为「伪新增」。⛔ 时长不得均分，须给依据。见 `references/phase-02-design.md` →「阶段归属矩阵」。
> 8. **结构模式须显式选型并给依据（v1.7 新增）**：≥2 天、或 ≥3 阶段、或含真实项目 / 客户现场 / 结业答辩的项目，定稿前必须落**三张前置卡**（出口绩效 / 任务清单 / 学员起点），并写明所选结构模式（P1 阶段块状 / P2 整体任务螺旋 / P3 案例阶梯 / P4 项目主线 / P5 混合旅程）**及判别矩阵中哪一问给出的答案**。⛔ 缺卡或写不出判别依据 → 方案只能标「**假设版结构**」并写明缺哪张、谁补；⛔ 不得宣称「最佳实践」。⛔ 学员首次见到完整链路不得晚于倒数第二个单元（否则触 A-1「全案后置」，须加回接）。⛔ 把商业约束下的妥协包装成最佳实践同样不合格——须同时给出被放弃的更优方案及放弃理由。见 `references/program-structure.md`。
> 9. **层级先对齐再谈结构（v1.8 新增）**：任何「结构」问题先定层级——**L1 课程体系**（多门课的进阶路径）/ **L2 培训项目**（一次干预的完整体验）/ **L3 课程**（一门课的模块）/ **L4 课次**（一次课的分钟轴）/ **L5 课堂**（分钟级活动）/ **L6 载体**（课件材料）。⛔ **结构类文档标题必须带层级标签**；⛔ **一章之内不得混用两层方法**（6Ds 不与 Gagné 同节）；⛔ 出现「课程体系」前须先答「有没有 ≥3 门课且有进阶关系」，没有就写「课程」；⛔ 禁止造「培训项目课程体系」这类跨层词。`术语对 ≠ 层级对`。见 `references/structure-levels.md`（L0-L6 表 + 判定口诀 + 6 条混用修正）。
> 10. **角色随阶段切换（v1.9 新增）**：每进入一个阶段，先答一句「本阶段主责哪个角色（体系架构师 L1 / 项目设计师 L2 / 课程设计师 L3 / 磨课师 L4-L5）+ 此刻用哪两项核心技能」。四角色判据**独立成表、不得互相顶替**——「排期合理」推不出「课程设计合理」。⛔ 同一阶段不得由两个角色同时主责（P03 例外：内容主责与课堂落地主责并列，冲突时以「能不能讲完」为硬约束删内容，**不得延长课时**）。⛔ 角色切换须留 4 行交接单（产出物 / 未决项 / 给下一角色的硬约束 / 本阶段被否方案），不得靠对话记忆。⛔ S 档（≤2 天、无客户现场、无答辩）不跑全矩阵，避免过度工程。见 `references/roles-and-stages.md`（六阶段 RACI + 四角色技能栈与失效条件 + S/M/L 分档 + 检查 6 问）。

## 阶段工作流

每个阶段三块描述：**前置输入 → 执行内容 → 产出物**。完成后产出物写盘，下次对话或另一实例可读取继续。

### Phase 01：分析阶段

**前置输入**：`00-培训需求spec.md`（如果已通过 course-discovery 产出）或无（新项目直接开始）

**执行**：读 `references/phase-01-analysis.md`，引导用户：
1. 业务需求拆解（痛点验证）
2. 学习者画像与情绪分析
3. 能力差距诊断（布卢姆分层）

**核心问题**：学习者的痛点是什么？他们为什么愿意花时间学这门课？

**产出物**：写入 `01-需求定位报告.md`（格式见 phase-01-reference 的"产出物结构"）

**阶段完成条件**：
- ✅ `01-需求定位报告.md` 已写入课程项目目录
- ✅ 已执行或已有明确计划的 P1 验证（3 名目标学员访谈，验证需求假设）
- ✅ 分析阶段检查清单（见 `references/common-tools.md`）全部通过



### Phase 02：设计阶段

> ⚠️ **v1.9 边界**：本阶段只做 **P02b 课程设计（L3）**——模块划分、学习目标、体验旅程、考核判据。
> **P02a 项目架构（L2：排几天 / 几天实战 / 客户哪天到场 / 转化与评估设计）不在本技能内**，归 `program-design` 技能，且**必须先于本阶段完成**。
> ⛔ 顺序颠倒 = 用 L3 的模块去凑 L2 的天数，必然凑出「天数用完了、内容还没完」（G-16 / G-18 的共同成因）。

**前置输入**：读 `01-需求定位报告.md`（无则退回 Phase 01）；若项目为 M / L 档，还须先有 `program-design` 产出的《培训项目架构方案》

**执行**：读 `references/phase-02-design.md`，引导用户：
1. 编写学习目标（布卢姆动词 + 可观测成果）
2. 设计学习体验旅程（情绪曲线）
3. 目标-内容-评估对齐矩阵
4. 叙事弧与认知节奏
5. 痛点/惊叫点/爽点检查

**核心问题**：惊叫点在哪里？学习旅程中有没有认知高潮？

**产出物**：写入 `02-课程设计方案.md`

**阶段完成条件**：
- ✅ `02-课程设计方案.md` 已写入课程项目目录
- ✅ **阶段归属矩阵已产出（v1.6）**：课程名拆段 → 每单元标称阶段（恰好 1 个）→ 逐活动 `活动/模块/阶段` 三列齐备；**跨阶段行 0**；每段时长有依据、非默认均分；新增单元三问均已作答
- ✅ **结构模式已有依据（v1.7 / v1.9 移交）**：三张前置卡（出口绩效 / 任务清单 / 学员起点）与结构模式已由 `program-design` 产出（M / L 档）；本阶段只**引用**其结论，不在本阶段重做；缺卡或标「假设版结构」者，本阶段须在方案首页继承同一标注
- ✅ **层级已声明（v1.8）**：设计文档标题带层级标签（L1 课程体系 / L2 培训项目 / L3 课程 / L4 课次）；「课程体系」一词仅在有 ≥3 门且有进阶关系时使用；文件内无跨层方法混用
- ✅ **角色已声明（v1.9）**：本阶段主责角色（课程设计师）+ 所用两项核心技能已写明；P02a（L2 项目架构）已由 `program-design` 完成并留下交接单，未越界重做
- ✅ 已执行或已有明确计划的 P2 验证（1 小时最小原型课试讲给 2-3 人）

### 版本管理规范

所有产出物文件在开发迭代过程中应遵循以下版本管理规范。

#### 版本状态四态

每个产出物文件处于以下四种状态之一：

| 状态 | 标签 | 含义 |
|:---|:---:|:---|
| ✅ Final | 定稿 | 经过评审，不再主动修改 |
| 🔍 Review | 审核中 | 待审核或审核中，可能还有调整 |
| 📝 Draft | 草稿 | 仍在写作/开发中 |
| ⏸ Superseded | 已替代 | 被新版替代，保留作为历史参考 |

#### 文件内 Changelog

每个产出物文件末尾必须包含 Changelog 区块，记录该文件的完整变更历史：

```markdown
---

## Changelog

| 日期 | 版本 | 改动 | 原因 |
|:---:|:---:|:---|:---|
| 07-18 | 1.1 | 课程名统一；课2 30→45min | 品牌统一 + 试讲反馈内容多 |
| 07-14 | 1.0 | 初版 | — |
```

**规则：**
- 版本号：语义化。第一版 `1.0`，每次重要改动 `+0.1`
- 原因栏不能空——每次改动必须写明原因（为什么改）
- 标注跨文件影响：如果改动影响其他文件，用 ⚠️ 标记

#### 项目级版本清单

项目根目录应放置 `VERSION.md`，一张表汇总所有产出物的当前版本和状态：

```markdown
# [项目名称] · 版本清单

| 文件 | 版本 | 状态 | 最后更新 | 本轮改动 |
|:---|:---:|:---:|:---:|:---|
| 00-培训需求spec.md | 1.1 | ✅ Final | 07-14 | 初版确认 |
| 02-课程设计方案.md | 1.1 | ✅ Final | 07-14 | 初版确认 |
| ... | ... | ... | ... | ... |
```

#### 迭代原则

1. **不原地修改**——迭代时保留前版的版本记录，在原文件末尾追加新 Changelog 行，不覆盖历史
2. **增量不重写**——每次改动应附着于前次版本之上，通过 Changelog 的行数增长体现迭代次数
3. **变更波及检查**——修改一个文件时，检查其 Changelog 中是否标记了 ⚠️ 影响其他文件。如涉及，同步更新关联文件的版本号和 Changelog
4. **规范变更后全包回归检索（v1.2 新增）**——凡专家包规范修订、评审整改、或改动被引用小节名/页名/物件名，须对**全部已产出文件**执行检索（词表与范围见 `references/common-tools.md`），不得以「其余 N 章未变」代替；被改文件 Changelog 标 ⚠️ 波及，并在项目 `VERSION.md` 登记命中分布与不变项量化
