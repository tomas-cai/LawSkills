# 评审方法论详细参考

本文档提供 5 个评审维度的详细检查项、质量清单和深度分级标准。SKILL.md 定义流程骨架，本文档定义检查细节。

## 维度 1：结构完整性 —— 详细检查清单

### Phase 01 分析阶段检查
- [ ] 需求来源是否明确？
- [ ] 是否完成了痛点验证（不只有一个需求方确认）？
- [ ] 是否识别了不适合培训解决的问题？
- [ ] 学习者画像是否包含了情绪起点分析？
- [ ] 能力差距诊断是否基于布卢姆分层？

### Phase 02 设计阶段检查
- [ ] 每条学习目标是否使用"行为动词 + 可观测成果"格式？
- [ ] 目标层级是否匹配业务期望？
- [ ] 是否设计了情绪曲线？不是只有内容大纲？
- [ ] 每条目标是否有对应的内容和测评？
- [ ] 是否有至少一个"惊叫点"设计？
- [ ] 是否有认知负荷管理策略？

### Phase 03 开发阶段检查
- [ ] 五侧材料是否全部到位？（大纲/学员/讲师/实操/测评 + 课件PPT）
- [ ] 目标-内容-测评是否对齐？
- [ ] 实操案例是否有明确决策点？
- [ ] 测评形式是否匹配布卢姆层级？
- [ ] 课件（05-课程课件）是否已完成？
- [ ] 课件内容是否与课程设计方案和学习手册完全对齐？
- [ ] 每张课件是否一页一个要点、无大段文字？

### Phase 04 实施阶段检查
- [ ] 是否做了前置测评？
- [ ] 是否需要分层教学？
- [ ] 是否有随堂形成性评估计划？
- [ ] 讲师引导手册是否包含时间分配和关键话术？

### Phase 05 评估阶段检查
- [ ] 是否覆盖了柯氏 L1-L4？
- [ ] 是否对每项目标做了达成度分析？
- [ ] 是否复验了最初的"痛点假设"？
- [ ] 是否输出了优先级明确的迭代计划？

## 维度 2：内部一致性 —— 追踪路径

### 目标人群一致性
从 Phase 01 出发，依次检查：
1. Phase 01：学员画像中的"岗位与经验层级"
2. Phase 02：学习目标的难度层级是否匹配该人群
3. Phase 03：案例中的角色设定和场景复杂度是否匹配
4. Phase 04：前置测评的难度是否匹配

### 痛点一致性
从 Phase 00/01 出发：
1. Phase 00/01："核心痛点"的具体描述
2. Phase 02：情绪曲线和惊叫点设计是否回应了痛点
3. Phase 03：讲师话术中是否有针对性的痛点回应
4. Phase 05：痛点复盘机制是否覆盖了最初定义的痛点

### 学习目标一致性
从 Phase 02 出发：
1. Phase 02：目标清单中的每条 OBJ
2. Phase 03：每条 OBJ 是否有对应的测评（ASSESS）
3. Phase 05：每个 OBJ 是否有达成度分析

## 维度 3：内容深度 —— 分级定义

| 深度层级 | 定义 | 判断标志 |
|:---|:---|:---|
| **L1 骨架级** | 文件存在，有结构，有占位符 | 有"待填写"标记，表格有空行 |
| **L2 填充级** | 内容完整，**学员侧与讲师侧分别可读**（v1.3） | 无占位符，每段落有实质性内容；学员正文脱离讲解也能读懂，讲师讲解层有逐字话术 |
| **L3 教学级** | 拿到就能上课，讲师不需额外准备 | 模拟一节课能讲下来，无盲区 |
| **L4 精品级** | 有视觉设计、录屏、课后扩展 | 学员体验完整，超出预期 |

**底线要求**：
- 全部产出物：L2 填充级
- 每张课件：L2 填充级
- Day 1 前 3 个模块：L3 教学级（讲师最难把握的部分）

> **v1.3 可读性主体声明**：「可读性强」必须**分别**按学员侧与讲师侧判定，不得用一份材料的字数 / 完整度代替。学员侧读不懂（半截句、设计目标语、只有结论没示例）或讲师侧不能讲（只有元数据、无逐字话术），任一不合格即该页不得计为 L2。标题须另按 `course-design/references/phase-03-development.md` →「学员视角标题契约」4 条判定。⛔ 禁止把「任务式标签词」当作合格标题。

## 维度 4：可教性 —— 检查细节

### 时间可行性
- [ ] 课程大纲中的时间段加起来 = 课程总时长
- [ ] 每个模块的"讲授时间"与"实操时间"比例合理
- [ ] 休息时间已预留
- [ ] 留白/问答时间已预留

### 讲师引导
- [ ] 讲师手册每个模块有时间分配
- [ ] 关键环节有逐字话术
- [ ] **打开课件任一页，讲解层（逐字话术）齐备，讲师不需翻手册即可开讲（v1.3 新增）**；⛔ 只列课次 / 页码 / 时长 / 要点条数的「讲师视图」判为不合格
- [ ] 常见学员反应有应对策略
- [ ] 技术环节有应急方案

### 案例可操作性
- [ ] 案例场景有充分上下文
- [ ] 决策节点有明确选项
- [ ] 参考答案有层次差异（好/中/差）
- [ ] 延展讨论有引导方向

### 测评可评分性
- [ ] 每条测评有评分标准
- [ ] 评分标准能区分优/中/差
- [ ] 权重分配合理（高层级测评 > 低层级测评）
- [ ] 有明确的"通过/不通过"分界线

## 维度 5：风险评估

### 风险类型清单

| 风险类型 | 例子 | 严重程度 |
|:---|:---|:---:|
| **技术依赖** | AI 工具不可用、API 限流、网络不稳定 | 高 |
| **讲师依赖** | 模块依赖某位讲师的经验才能讲好 | 中 |
| **学员差异** | 学员基础跨度大，分层后某一层不足 | 中 |
| **内容时效** | 引用工具/数据已过时 | 中 |
| **复杂度超限** | 模块内容太多，时间不够 | 低-中 |

### 风险评估模板

```
风险：[描述具体风险]
影响：[什么情况下哪些环节会出问题]
概率：高 / 中 / 低
严重程度：高 / 中 / 低
应对预案：[具体行动，不少于 2 条]
```

## 维度 3：内容深度 —— 新增检查项

### 适用课程类型声明（v1.2 新增，先判类型再选判据）

> 本维度与维度 4 的技术类检查项（终端形态 / 推荐技术栈 / AGENTS.md）**全部面向 A 类「AI 软件开发 · 构建型」课程**。第二次实战的「业务咨询 + AI 落地实施」课属 B 类，评审者只能自行做等价映射，既可能误扣分也可能漏检（缺陷 G-2）。
> **评审第一步**：判定课程类型、写进评审报告「总体评估」，再按下表选列。**A 类判据原样保留**；B / C 类用等价判据；不得因「没有技术栈 / 没有 AGENTS.md」直接扣分，也不得跳过内容深度检查。

| 类型 | 典型课程 | 维度 3 用哪一列 | 维度 4 用哪一列 |
|:---|:---|:---|:---|
| **A · AI 软件开发 / 构建型** | 前端开发、AI 应用开发、Agent 工程 | A 列（原有技术判据） | A 列（原有技术依赖预警） |
| **B · 业务咨询 + AI 落地实施** | 业务场景梳理、方案设计、智能体实施、FDE 培养 | **B 列（等价判据，见下表）** | **B 列（等价判据，见下）** |
| **C · 通用软技能 / 管理 / 合规** | 沟通、领导力、制度与合规培训 | C 列（情境真实度 / 决策点） | C 列（角色扮演 / 材料依赖） |

**B 类等价判据（非软件开发类，逐项可勾选）**

| 原 A 类检查项 | B 类等价判据 | 常见缺失 |
|:---|:---|:---|
| 终端形态标注 | **承载形态**：交付物是方案文档 / 智能体 / 应用 / Skill / 表格 / 流程图中的哪一种，谁在什么场合用 | 只说「做个 AI 工具」，学员不知道交什么 |
| 推荐技术栈 | **实现环境与平台可接入性**：至少一个可演示环境、数据可接入性说明、**≥1 份非本期平台实现对照**；平台名不得进入学习目标与达标判据 | 把课程变成某平台操作教学，或演示环境开课当天不可用 |
| AGENTS.md 配置示例 | **数据契约与配置约定**：输入字段、数据来源、质量基线、口径定义、异常兜底 | 收益测算表无基线数据，搭建时才发现「资料根本没接入」 |
| 技术依赖 | **兜底 / 降级 / 开课前试跑**：外部 API 不可用时的降级路径、离线演示材料、试跑记录 | 断网 / 限流即全线停摆，无 B 计划 |
| 教学价值与课程目标对应 | 保留原判据（**A / B / C 通用**） | 案例与目标脱节 |

**C 类**：无构建产物时，维度 3 改查「情境真实度 / 角色卡 / 明确决策点 / 反馈量规」，维度 4 改查「角色扮演材料、分组与场地、无工具依赖」；A 类技术项统一标 **N/A（课程类型不适用）并写明理由**，不计为缺失。

### 实操案例质量检查

每个实操案例应包含以下要素：

| 要素 | 检查标准 | 常见缺失 | 适用课程类型（v1.2 增列） |
|:---|:---|:---|:---:|
| **终端形态标注** | 明确标注 Mobile APP / PC Web / 纯评估练习 | 缺失 → 学员不知道按什么屏幕尺寸设计 | **A**（B 用「承载形态」） |
| **推荐技术栈** | 给出 1-2 个推荐框架 + 选择理由 | 缺失 → 学员不知道该在 AGENTS.md 中声明什么 | **A**（B 用「实现环境与可接入性」） |
| **AGENTS.md 配置示例**（如适用） | 给出该技术栈的 AGENTS.md 声明片段 | 缺失 → 学员不知道规范怎么写 | **A**（B 用「数据契约」） |
| **技术依赖** | 明确标注需要/不需要外部 API 或降级方案 | 缺失 → 开课时才发现工具不可用 | **A / B**（B 用「兜底 / 降级 / 试跑」） |
| **教学价值与课程目标的对应** | 每个案例标明它对应课程的哪个核心教学维度 | 缺失 → 学员不知道为什么做这个案例 | **A / B / C（通用）** |

## 维度 6：格式一致性（跨文档格式变更审计）

> 当课程交付格式发生变更时（如 2 天→2 周、线下→线上、讲座→翻转），独立的文件更新容易被遗漏。
> 本维度专门检查所有文档是否统一使用新格式的术语和结构。

### 审计步骤

1. **确定当前格式的"关键术语表"**

   提取 `00-课程大纲.md` 或 `02-课程设计方案.md` 中的核心格式关键词，作为审计基准：

   | 格式维度 | 示例关键词 |
   |:---|:---|
   | 周期 | "2 周", "2 天", "5 天" |
   | 授课模式 | "翻转课堂", "直播", "微课", "录播" |
   | 节奏描述 | "课 1", "W1", "Day 1", "09:00" |
   | 时长 | "30min", "45min", "8h", "16 小时" |
   | 交付平台 | "线上直播", "线上录播", "线下" |
   | 学员角色 | "学员自主", "讲师主讲" |

2. **扫描所有文档**

   对课程项目目录下的每个 `.md` 文件，逐个检查是否仍有**旧格式**的术语残留。

   常见旧术语：
   ```
   "Day 1" / "Day 2"          ← 旧的是"天"，新的是"课"
   "09:00" / "18:00"          ← 旧的是紧凑时间表，新的是弹性
   "2 天"（在非描述性位置）     ← 旧时长
   "16 小时"                   ← 旧时长
   "签到 + 课前摸底"           ← 旧流程
   "讲师点评 + 证书颁发"       ← 旧流程
   ```

3. **逐个修复确认**

   发现旧术语后，确认是否需要替换。判断标准：
   - 如果是**文档主体的描述性内容** → 必须替换
   - 如果是**引用旧文档的元数据**（如"此前版本为 2 天"）→ 可保留但需标注
   - 如果是**客观历史记载**（如 Phase 00 的原始需求）→ 无需替换

### 检查清单

- [ ] 周期描述（2 天 / 2 周 / 5 周）在各文档中一致
- [ ] 时间表格式（Day 1/Day 2 或 课 1/课 2）在各文档中一致
- [ ] 交付模式（讲座 / 翻转 / 混合）在各文档中一致
- [ ] 学员角色描述在各文档中一致
- [ ] 旧格式的遗留术语已全部清除
- [ ] 格式变更后新引入的文件（如微课脚本）也使用了新格式的术语

> **注意**：格式一致性检查的触发条件是"已知格式变更发生"。如果课程从头到尾都是同一个格式（如一直是翻转课堂），则不需要执行本维度。


## 维度 7：Phase 03 三角对齐（大纲 ⇄ 学员手册 ⇄ 讲师手册）

> 三个交付文件是"三角关系"——任何一个脱节，教学现场就会出现"大纲写了但讲师没讲"或"讲师讲了但学员手册没有"的断裂。

### 检查路径

沿"大纲 → 学员手册 → 讲师手册"这条链逐课时检查，确保三个文件对每个课时的描述一致。

```
每个课时 → 大纲写了什么 → 学员手册对照 → 讲师手册对照
```

### 检查清单

#### 课时结构对齐

对每个课时/模块，检查三个文件是否一致：

| 检查项 | 学员手册 vs 大纲 | 讲师手册 vs 大纲 | 讲师手册 vs 学员手册 |
|:---|:---:|:---:|:---:|
| **课时主题名称** | 主题名一致 | 主题名一致 | — |
| **课时顺序** | 模块顺序一致 | 模块顺序一致 | — |
| **核心内容** | 大纲列的内容在手册中有对应章节 | 大纲列的内容在讲稿中有对应环节 | 讲稿中涉及的关键概念在手册中有说明 |
| **练习/作业** | 大纲列的练习在手册中有描述 | 大纲列的练习在讲稿中有引导流程 | 讲稿中引导的练习对手册描述一致 |
| **时长/节奏** | — | 讲稿的时间分配与大綱一致 | — |

#### 典型断裂

| 断裂类型 | 示例 | 后果 |
|:---|:---|:---|
| **大纲有、手册无** | 大纲写"课 2：规范驱动重做"，学员手册无 AGENTS.md 模板 | 学员课后无法复习 |
| **大纲有、讲稿无** | 大纲写"课 2 分享优秀作业 10min"，讲师手册无此环节 | 讲师忘记这个环节，互动缺失 |
| **讲稿有、手册无** | 讲师现场讲了一个案例，学员手册没有 | 学员记不住，课后无法回看 |
| **三者不一致** | 大纲写"课 1：体验"，手册写"课 1：入门"，讲稿写"课 1：案例 1" | 学员困惑，不知道这节课主题是什么 |

### 检查方法

1. **逐课时阅读大纲**，列出每个课时的：主题名、核心内容、练习、时长
2. **打开学员手册**，检查大纲列出的每项内容在手册中是否有对应章节
3. **打开讲师手册**，检查大纲列出的每项内容在讲稿中是否有对应环节
4. **交叉检查**：讲师手册中提到的关键概念/案例，学员手册中是否有说明

## 维度 8：变更冲突检查（新增内容 vs 已有内容）

> 当有人提议在课程项目中**新增**一个模块/环节/主题时，在正式落地之前，
> 必须检查它会不会与已有的内容产生**主题重叠、目标冲突或节奏干扰**。

### 检查步骤

**步骤 1：确定新增内容的主题边界**

用一句话明确新增内容的核心命题。例如：
> "新增主题：AI 产品经理的角色认知——讲 AI 时代为什么诞生了这个岗位、薪资趋势、典型工作日常"

**步骤 2：定位可能重叠的已有内容**

沿着课程大纲，检查所有与新增内容关键词相关的已有课时。关键词匹配示例：

| 新增内容关键词 | 扫瞄大纲中的所有课时 | 重点关注 |
|:---|:---|:---|
| "AI PM"、"角色"、"认知"、"趋势" | 课 1 M1、课 1 AI PM vs 传统 PM、课 2 质量揭秘 | 课 1 是否有同类概念讲解？ |

**步骤 3：逐项比对（核心操作）**

打开疑似重叠的已有课时的大纲描述 + PPT 内容，逐项比对：

| 比对维度 | 已有内容讲了什么 | 新增内容要讲什么 | 是否重叠 |
|:---|:---|:---|:---:|
| **核心命题** | 两个 demo 质量对比（体验） | AI PM 岗位出现的宏观原因（认知） | ✅ 互补 |
| **知识层级** | 技能层（怎么做） | 认知层（为什么做） | ✅ 不冲突 |
| **受众价值** | 体验 AI 输出差异 | 理解 AI PM 的职业前景 | ✅ 不同 |
| **交付形式** | 讲师操作演示 | 讲师讲述 + 数据展示 | ✅ 不同 |

**步骤 4：判断结论**

| 结论 | 含义 | 行动 |
|:---|:---|:---|
| **无重叠** | 新增内容与已有内容互补，可落地 | 进入开发 |
| **部分重叠但可合并** | 核心信息有交叉但侧重点不同 | 调整边界后落地 |
| **高度重叠** | 新增内容已有现有模块覆盖 | 不落地，或替换现有内容 |

### 变更冲突检查清单

- [ ] 已用一句话明确新增内容的主题边界
- [ ] 已扫描大纲中所有相关课时的描述
- [ ] 已打开疑似重叠课时的 PPT 做内容级比对
- [ ] 已从核心命题/知识层级/受众价值/交付形式 4 个维度做比对
- [ ] 比对结论已记录
