# 写作风格规范

把“我想写得像这样”转化为后续 Skill 能稳定读取的规则。只记录可观察、可检验的特征，不把抽象形容词直接当作规则。

## 输入检查

先建立六格需求卡：

| 字段 | 必须回答的问题 |
|---|---|
| 问题 | 这套风格要解决什么写作问题？ |
| 场景 | 用于什么平台、栏目、文体和阅读场景？ |
| 输入 | 有哪些示例、禁用词、品牌资料或历史稿件？ |
| 输出 | 需要规则文件、示例、还是同时产出一篇试写稿？ |
| 规则 | 必须保留的语气、结构、格式、长度是什么？ |
| 禁止 | 哪些表达、事实处理和排版方式不能出现？ |

没有示例时，先把用户描述标记为“待验证偏好”，不要把它伪装成已验证风格。

## 工作流程

1. 读取示例，区分正文、标题、列表、引用、结尾和平台格式；至少使用 2 篇同类样文才能总结稳定特征。
2. 从以下维度提取证据：目标读者、写作目的、语气、叙述视角、句子节奏、段落长度、结构习惯、词汇偏好、修辞密度、标题模式、行动号召、标点与 Markdown/HTML 规则。
3. 把每条规则写成“条件 + 动作 + 可检查标准”，例如“面向初学者解释术语时，先给一句白话定义，再给一个工作场景例子”。为规则保留样文证据或 `evidence: 用户指定`。
4. 处理冲突：按用户明确要求 > 目标平台规范 > 多数样文共同特征 > 单篇样文特征排序；仍无法判断时列入待确认项。
5. 生成 `style-guide.md` 与 `style-rules.json`。如果用户未指定目录，在回复中给出完整内容，不擅自写入不明确的位置。
6. 用下面的自检清单复核，确保规则能被另一个 Skill 直接执行。

## 产物契约

`style-guide.md` 至少包含：

- 风格定位、适用场景与不适用场景
- 硬约束、软偏好、禁止项
- 标题、开头、正文段落、结尾的写法
- 正反例各 1 组；正例必须是新写的示例，不抄录样文
- 未决项与验证方式

`style-rules.json` 使用以下结构，缺省项写 `null` 或空数组，不省略关键字段：

```json
{
  "version": "1.0",
  "language": "zh-CN",
  "audience": "",
  "purpose": "",
  "contexts": [],
  "tone": {"primary": "", "secondary": [], "avoid": []},
  "voice": {"person": "", "stance": "", "formality": ""},
  "structure": {"opening": "", "body": [], "ending": "", "max_heading_depth": 3},
  "sentence_style": {"length": "", "rhythm": "", "paragraph_length": ""},
  "vocabulary": {"preferred": [], "avoid": [], "terms": {}},
  "formatting": {"markdown": true, "list_style": "", "punctuation": ""},
  "length": {"min_words": null, "max_words": null},
  "hard_rules": [],
  "soft_preferences": [],
  "evidence": [],
  "open_questions": []
}
```

后续 Skill 加载风格时，优先读取 `style-rules.json`，再读取 `style-guide.md` 获取解释与示例。不要把风格规则与本次文章事实混在同一个文件里。

## 质量门禁

- [ ] 每条硬规则都能通过文本观察或计数检查。
- [ ] 禁止项不会与必需的平台格式冲突。
- [ ] 没有把单篇样文的偶然表达误判为长期风格。
- [ ] 没有复制样文中的事实、金句或未经授权的独特表达。
- [ ] 已标出未决项、证据来源和需要人工确认的选择。
