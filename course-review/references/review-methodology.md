# 评审方法论详细参考

本文档提供 5 个评审维度的详细检查项、质量清单和深度分级标准。SKILL.md 定义流程骨架，本文档定义检查细节。

## 维度 1：结构完整性 —— 详细检查清单

### Phase 01 分析阶段检查
- [ ] 需求来源是否明确？
- [ ] 是否完成了痛点验证（不只有一个需求方确认）？
- [ ] 是否识别了不适合培训解决的问题？
- [ ] 学习者画像是否包含了情绪起点分析？
- [ ] 能力差距诊断是否基于布卢姆分层？

### Phase 02 设计阶段检查
- [ ] 每条学习目标是否使用"行为动词 + 可观测成果"格式？
- [ ] 目标层级是否匹配业务期望？
- [ ] 是否设计了情绪曲线？不是只有内容大纲？
- [ ] 每条目标是否有对应的内容和测评？
- [ ] 是否有至少一个"惊叫点"设计？
- [ ] 是否有认知负荷管理策略？

### Phase 03 开发阶段检查
- [ ] 五侧材料是否全部到位？（大纲/学员/讲师/实操/测评 + 课件PPT）
- [ ] 目标-内容-测评是否对齐？
- [ ] 实操案例是否有明确决策点？
- [ ] 测评形式是否匹配布卢姆层级？
- [ ] 课件（05-课程课件）是否已完成？
- [ ] 课件内容是否与课程设计方案和学习手册完全对齐？
- [ ] 每张课件是否一页一个要点、无大段文字？

### Phase 04 实施阶段检查
- [ ] 是否做了前置测评？
- [ ] 是否需要分层教学？
- [ ] 是否有随堂形成性评估计划？
- [ ] 讲师引导手册是否包含时间分配和关键话术？

### Phase 05 评估阶段检查
- [ ] 是否覆盖了柯氏 L1-L4？
- [ ] 是否对每项目标做了达成度分析？
- [ ] 是否复验了最初的"痛点假设"？
- [ ] 是否输出了优先级明确的迭代计划？

## 维度 2：内部一致性 —— 追踪路径

### 目标人群一致性
从 Phase 01 出发，依次检查：
1. Phase 01：学员画像中的"岗位与经验层级"
2. Phase 02：学习目标的难度层级是否匹配该人群
3. Phase 03：案例中的角色设定和场景复杂度是否匹配
4. Phase 04：前置测评的难度是否匹配

### 痛点一致性
从 Phase 00/01 出发：
1. Phase 00/01："核心痛点"的具体描述
2. Phase 02：情绪曲线和惊叫点设计是否回应了痛点
3. Phase 03：讲师话术中是否有针对性的痛点回应
4. Phase 05：痛点复盘机制是否覆盖了最初定义的痛点

### 学习目标一致性
从 Phase 02 出发：
1. Phase 02：目标清单中的每条 OBJ
2. Phase 03：每条 OBJ 是否有对应的测评（ASSESS）
3. Phase 05：每个 OBJ 是否有达成度分析

## 维度 3：内容深度 —— 分级定义

| 深度层级 | 定义 | 判断标志 |
|:---|:---|:---|
| **L1 骨架级** | 文件存在，有结构，有占位符 | 有"待填写"标记，表格有空行 |
| **L2 填充级** | 内容完整，可读性强 | 无占位符，每段落有实质性内容 |
| **L3 教学级** | 拿到就能上课，讲师不需额外准备 | 模拟一节课能讲下来，无盲区 |
| **L4 精品级** | 有视觉设计、录屏、课后扩展 | 学员体验完整，超出预期 |

**底线要求**：
- 全部产出物：L2 填充级
- 每张课件：L2 填充级
- Day 1 前 3 个模块：L3 教学级（讲师最难把握的部分）

## 维度 4：可教性 —— 检查细节

### 时间可行性
- [ ] 课程大纲中的时间段加起来 = 课程总时长
- [ ] 每个模块的"讲授时间"与"实操时间"比例合理
- [ ] 休息时间已预留
- [ ] 留白/问答时间已预留

### 讲师引导
- [ ] 讲师手册每个模块有时间分配
- [ ] 关键环节有逐字话术
- [ ] 常见学员反应有应对策略
- [ ] 技术环节有应急方案

### 案例可操作性
- [ ] 案例场景有充分上下文
- [ ] 决策节点有明确选项
- [ ] 参考答案有层次差异（好/中/差）
- [ ] 延展讨论有引导方向

### 测评可评分性
- [ ] 每条测评有评分标准
- [ ] 评分标准能区分优/中/差
- [ ] 权重分配合理（高层级测评 > 低层级测评）
- [ ] 有明确的"通过/不通过"分界线

## 维度 5：风险评估

### 风险类型清单

| 风险类型 | 例子 | 严重程度 |
|:---|:---|:---:|
| **技术依赖** | AI 工具不可用、API 限流、网络不稳定 | 高 |
| **讲师依赖** | 模块依赖某位讲师的经验才能讲好 | 中 |
| **学员差异** | 学员基础跨度大，分层后某一层不足 | 中 |
| **内容时效** | 引用工具/数据已过时 | 中 |
| **复杂度超限** | 模块内容太多，时间不够 | 低-中 |

### 风险评估模板

```
风险：[描述具体风险]
影响：[什么情况下哪些环节会出问题]
概率：高 / 中 / 低
严重程度：高 / 中 / 低
应对预案：[具体行动，不少于 2 条]
```

## 维度 3：内容深度 —— 新增检查项

### 实操案例质量检查

每个实操案例应包含以下要素：

| 要素 | 检查标准 | 常见缺失 |
|:---|:---|:---|
| **终端形态标注** | 明确标注 Mobile APP / PC Web / 纯评估练习 | 缺失 → 学员不知道按什么屏幕尺寸设计 |
| **推荐技术栈** | 给出 1-2 个推荐框架 + 选择理由 | 缺失 → 学员不知道该在 AGENTS.md 中声明什么 |
| **AGENTS.md 配置示例**（如适用） | 给出该技术栈的 AGENTS.md 声明片段 | 缺失 → 学员不知道规范怎么写 |
| **技术依赖** | 明确标注需要/不需要外部 API 或降级方案 | 缺失 → 开课时才发现工具不可用 |
| **教学价值与课程目标的对应** | 每个案例标明它对应课程的哪个核心教学维度 | 缺失 → 学员不知道为什么做这个案例 |

### 技术栈选型合理性检查

| 检查项 | 标准 |
|:---|:---|
| Tailwind CSS → C 端 PC Web | 简历工具、内容型前台页面 ✅ |
| Nuxt UI / Tailwind 移动端优先 → Mobile APP | 面试训练、碎片场景工具 ✅ |
| Ant Design Pro / Element Plus → 后台管理 | CRM、数据后台、运营后台 ✅ |
| 技术栈是否与 AGENTS.md 中的 UI 约束一致？ | AGENTS.md 中声明的框架必须与推荐一致 |

## 维度 4：可教性 —— 新增检查项

### 技术依赖预警

- [ ] 每个构建型案例是否标注了"推荐技术栈"？
- [ ] 推荐的框架是否需要学员课前预习？（如 Ant Design 概念）
- [ ] 如果需要预习，是否有课前资料准备清单？
- [ ] 是否有多框架备选方案？（如学员不熟悉 React 可以用 Vue 版 Element Plus）
- [ ] 是否标注了"技术依赖"（外部 API / AI 工具 / 降级方案）？

## 本阶段完成检查（新增）

- [ ] 实操案例均已标注终端形态
- [ ] 实操案例均已标注推荐技术栈
- [ ] 构建型案例均有 AGENTS.md 配置示例
- [ ] 技术栈选择匹配终端形态
- [ ] 技术依赖均已标注降级方案

## 维度 6：格式一致性（跨文档格式变更审计）

> 当课程交付格式发生变更时（如 2 天→2 周、线下→线上、讲座→翻转），独立的文件更新容易被遗漏。
> 本维度专门检查所有文档是否统一使用新格式的术语和结构。

### 审计步骤

1. **确定当前格式的"关键术语表"**

   提取 `00-课程大纲.md` 或 `02-课程设计方案.md` 中的核心格式关键词，作为审计基准：

   | 格式维度 | 示例关键词 |
   |:---|:---|
   | 周期 | "2 周", "2 天", "5 天" |
   | 授课模式 | "翻转课堂", "直播", "微课", "录播" |
   | 节奏描述 | "课 1", "W1", "Day 1", "09:00" |
   | 时长 | "30min", "45min", "8h", "16 小时" |
   | 交付平台 | "线上直播", "线上录播", "线下" |
   | 学员角色 | "学员自主", "讲师主讲" |

2. **扫描所有文档**

   对课程项目目录下的每个 `.md` 文件，逐个检查是否仍有**旧格式**的术语残留。

   常见旧术语：
   ```
   "Day 1" / "Day 2"          ← 旧的是"天"，新的是"课"
   "09:00" / "18:00"          ← 旧的是紧凑时间表，新的是弹性
   "2 天"（在非描述性位置）     ← 旧时长
   "16 小时"                   ← 旧时长
   "签到 + 课前摸底"           ← 旧流程
   "讲师点评 + 证书颁发"       ← 旧流程
   ```

3. **逐个修复确认**

   发现旧术语后，确认是否需要替换。判断标准：
   - 如果是**文档主体的描述性内容** → 必须替换
   - 如果是**引用旧文档的元数据**（如"此前版本为 2 天"）→ 可保留但需标注
   - 如果是**客观历史记载**（如 Phase 00 的原始需求）→ 无需替换

### 检查清单

- [ ] 周期描述（2 天 / 2 周 / 5 周）在各文档中一致
- [ ] 时间表格式（Day 1/Day 2 或 课 1/课 2）在各文档中一致
- [ ] 交付模式（讲座 / 翻转 / 混合）在各文档中一致
- [ ] 学员角色描述在各文档中一致
- [ ] 旧格式的遗留术语已全部清除
- [ ] 格式变更后新引入的文件（如微课脚本）也使用了新格式的术语

> **注意**：格式一致性检查的触发条件是"已知格式变更发生"。如果课程从头到尾都是同一个格式（如一直是翻转课堂），则不需要执行本维度。


## 维度 7：Phase 03 三角对齐（大纲 ⇄ 学员手册 ⇄ 讲师手册）

> 三个交付文件是"三角关系"——任何一个脱节，教学现场就会出现"大纲写了但讲师没讲"或"讲师讲了但学员手册没有"的断裂。

### 检查路径

沿"大纲 → 学员手册 → 讲师手册"这条链逐课时检查，确保三个文件对每个课时的描述一致。

```
每个课时 → 大纲写了什么 → 学员手册对照 → 讲师手册对照
```

### 检查清单

#### 课时结构对齐

对每个课时/模块，检查三个文件是否一致：

| 检查项 | 学员手册 vs 大纲 | 讲师手册 vs 大纲 | 讲师手册 vs 学员手册 |
|:---|:---:|:---:|:---:|
| **课时主题名称** | 主题名一致 | 主题名一致 | — |
| **课时顺序** | 模块顺序一致 | 模块顺序一致 | — |
| **核心内容** | 大纲列的内容在手册中有对应章节 | 大纲列的内容在讲稿中有对应环节 | 讲稿中涉及的关键概念在手册中有说明 |
| **练习/作业** | 大纲列的练习在手册中有描述 | 大纲列的练习在讲稿中有引导流程 | 讲稿中引导的练习对手册描述一致 |
| **时长/节奏** | — | 讲稿的时间分配与大綱一致 | — |

#### 典型断裂

| 断裂类型 | 示例 | 后果 |
|:---|:---|:---|
| **大纲有、手册无** | 大纲写"课 2：规范驱动重做"，学员手册无 AGENTS.md 模板 | 学员课后无法复习 |
| **大纲有、讲稿无** | 大纲写"课 2 分享优秀作业 10min"，讲师手册无此环节 | 讲师忘记这个环节，互动缺失 |
| **讲稿有、手册无** | 讲师现场讲了一个案例，学员手册没有 | 学员记不住，课后无法回看 |
| **三者不一致** | 大纲写"课 1：体验"，手册写"课 1：入门"，讲稿写"课 1：案例 1" | 学员困惑，不知道这节课主题是什么 |

### 检查方法

1. **逐课时阅读大纲**，列出每个课时的：主题名、核心内容、练习、时长
2. **打开学员手册**，检查大纲列出的每项内容在手册中是否有对应章节
3. **打开讲师手册**，检查大纲列出的每项内容在讲稿中是否有对应环节
4. **交叉检查**：讲师手册中提到的关键概念/案例，学员手册中是否有说明

### 快速检查表（适用于评审报告）

| 课时 | 大纲 | 学员手册 | 讲师手册 | 状态 |
|:---|:---|:---|:---|:---:|
| 课 1：体验 | 自由手搓演示 | 有 M4 章节 | 有直播环节 | ✅ |
| 课 2：跃迁 | AGENTS 模板 + 质量揭秘 | 有 AGENTS 模板 | 有揭秘环节 | ✅ |
| ... | ... | ... | ... | ... |

### 全域三角对齐：Phase 03 五文件互锁

实操案例和测评方案也应纳入三角对齐。五个文件不是各自独立的，是互为参照的：

```
        课程大纲（节奏母版）
          ╱  │  ╲
        ╱    │    ╲
      ╱      │      ╲
  学员手册   讲师手册   测评方案
      ╲      │      ╱
        ╲    │    ╱
          ╲  │  ╱
         实操案例（场景底座）
```

#### 新增检查项

| 链条 | 检查什么 | 常见断裂 |
|:---|:---|:---|
| **学员手册 ⇄ 实操案例** | 手册 M4/M6 练习引用的案例名是否在实操案例文件中存在？ | 手册写了"用简历助手练习"，但实操案例中简历助手的场景描述已被修改 |
| **讲师手册 ⇄ 实操案例** | 讲师手册 M4/M6 引导的练习场景是否从实操案例中提取的？ | 讲师在课中临时改了一个场景，但学员手册和实操案例没有同步更新 |
| **讲师手册 ⇄ 测评方案** | 讲师手册中的作业指引和评审标准，是否与测评方案的评分标准一致？ | 讲师手册写"提交即可通过"，测评方案要求"AGENTS.md ≥3 项"——冲突 |
| **大纲 ⇄ 测评方案** | 测评方案中的 ASSESS 时机是否与大綱的课次安排一致？ | 测评方案写"ASSESS-03 课 2 课后"，但大纲的课 2 没有安排相应的练习 |

#### 五文件互锁快速核验表

| 文件 | 依赖文件 | 核验方法 | 时间 |
|:---|:---|:---|:---|
| 课程大纲 | — | 基准文件，其他所有文件以此为参照 | 先读 |
| 学员手册 | 大纲 | 大纲中的每个课时，手册中都有对应章节 | 逐课时 |
| 讲师手册 | 大纲 | 大纲中的每个课时，讲稿中都有对应引导环节 | 逐课时 |
| 讲师手册 | 学员手册 | 讲稿中提到的核心概念，手册中都有说明 | 逐概念 |
| 讲师手册 | 测评方案 | 作业/评审指引与测评标准的评分维度一致 | 逐作业 |
| 实操案例 | 学员手册 | 手册提到的案例名在实操案例文件中存在 | 案例名 |
| 实操案例 | 讲师手册 | 讲稿引导的练习场景与实操案例的场景一致 | 场景描述 |
| 测评方案 | 大纲 | ASSESS 时机与大綱课次安排一致 | 逐 ASSESS |
| 测评方案 | 实操案例 | ASSESS 场景与实操案例的案例一致 | 逐场景 |


## 维度 8：变更冲突检查（新增内容 vs 已有内容）

> 当有人提议在课程项目中**新增**一个模块/环节/主题时，在正式落地之前，
> 必须检查它会不会与已有的内容产生**主题重叠、目标冲突或节奏干扰**。

### 检查步骤

**步骤 1：确定新增内容的主题边界**

用一句话明确新增内容的核心命题。例如：
> "新增主题：AI 产品经理的角色认知——讲 AI 时代为什么诞生了这个岗位、薪资趋势、典型工作日常"

**步骤 2：定位可能重叠的已有内容**

沿着课程大纲，检查所有与新增内容关键词相关的已有课时。关键词匹配示例：

| 新增内容关键词 | 扫瞄大纲中的所有课时 | 重点关注 |
|:---|:---|:---|
| "AI PM"、"角色"、"认知"、"趋势" | 课 1 M1、课 1 AI PM vs 传统 PM、课 2 质量揭秘 | 课 1 是否有同类概念讲解？ |

**步骤 3：逐项比对（核心操作）**

打开疑似重叠的已有课时的大纲描述 + PPT 内容，逐项比对：

| 比对维度 | 已有内容讲了什么 | 新增内容要讲什么 | 是否重叠 |
|:---|:---|:---|:---:|
| **核心命题** | 两个 demo 质量对比（体验） | AI PM 岗位出现的宏观原因（认知） | ✅ 互补 |
| **知识层级** | 技能层（怎么做） | 认知层（为什么做） | ✅ 不冲突 |
| **受众价值** | 体验 AI 输出差异 | 理解 AI PM 的职业前景 | ✅ 不同 |
| **交付形式** | 讲师操作演示 | 讲师讲述 + 数据展示 | ✅ 不同 |

**步骤 4：判断结论**

| 结论 | 含义 | 行动 |
|:---|:---|:---|
| **无重叠** | 新增内容与已有内容互补，可落地 | 进入开发 |
